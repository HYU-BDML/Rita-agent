# 8주 직접사용 제품과 사업모델 검토

작성: 2026-09-29. 사용자 제약: 학생 2명, 각 주 4–5시간. 계획에는 각 주 4.5시간 × 8주 = 36시간, 합계 72시간을 사용한다. 학생 한 명이 개발을 맡으면 실제 개발 예산은 36시간이다. 추가 실비 30만원은 개발 인건비가 아니다. 아래 시간은 견적이나 납기 보증이 아니라 범위를 줄이기 위한 계획 가정이다.

## 1. 결론

**초대받은 대행사 담당자 한 명이 고객사 브랜드 한 개의 카드뉴스를 직접 만들고, 고치고, 확정하고, PNG와 캡션을 받는 제한 제품은 시도할 가치가 있다.** 단, 기존 자산을 곧바로 공개 SaaS로 바꾸는 36시간짜리 작업이라고 약속하면 안 된다. 기존 소스는 렌더·부분 수정 재료를 제공하지만, 외부 고객의 로그인·데이터 격리·안정적 작업 처리·버전 확정이 완성되어 있지는 않다.

권고는 학생 72시간에 더해 **숙련 개발자 16–24시간을 별도 배정**해 연결·권한·배포·복구를 책임지게 하는 것이다. 이 시간을 확보하지 못하면 첫 고객이 직접 조작하는 제한 시험으로만 운영하고, 상시 이용 가능한 유료 SaaS 출시를 약속하지 않는다. 범용 편집기·여러 고객사·여러 사용자·고객 승인 포털·SNS 자동 발행은 이번 8주 범위에서 제외한다.

직접사용 기준은 분명하다. 담당자가 브랜드 자료를 넣고, 카드 문구를 수정하고, 확정본을 내려받는 동안 운영자가 뒤에서 파일을 고쳐 주지 않아야 한다. 사람이 제작해 전달한 납품팩에 대한 결제는 결과물 수요의 증거이며, 소프트웨어 직접사용 수요의 증거와 분리한다.

## 2. 현재 자산이 덜어주는 일과 새로 해야 하는 일

| 이미 있는 구현 재료 | 덜어주는 일 | 남는 일 |
|---|---|---|
| 덱 JSON→PNG 렌더 (`server.py` 25–43행) | 이미지 출력 엔진을 처음부터 만들 필요 감소 | 상업용 템플릿 품질, 과밀 텍스트 처리, 작업 제한, 오류 복구 |
| `_deck.json` 보관·부분 수정 (`부분수정.py` 4–22·64–71행) | 카드 내용을 구조화해 보관하고 일부 바꾸는 출발점 | 명시적 폼 편집, 버전 확정, 사용자별 접근 통제 |
| 큰 미리보기·썸네일·수정 요청 (`손질판.py` 60행 이후) | 보기→수정→다시 렌더 흐름을 참고 가능 | 외부 고객에게 이해되는 UI, 저장/작업 상태, 내보내기 묶음 |
| Dify 카드 문구·유형별 규칙 | 원고 작성 규칙 재사용 | 브랜드 조건·근거 전달·구조 오류 처리·원가 측정 |
| 트렌드 도구 | 이후 소재 탐색 모듈의 출발점 | 이번 범위에서는 연결하지 않아도 됨. 고객 제공 자료부터 시작 |

기존 `server.py`에는 `/파일` 경로의 서버 파일 보기·저장 기능(1396–1405, 1579–1599행), 공개 `/out/` 결과 경로(1561–1568행)가 함께 있다. 확인한 핸들러에서 고객별 인증·권한 경계를 확인하지 못했다. 이는 **현재 공개 서비스에 대한 침투 시험이나 취약성 확정이 아니다.** 새 고객용 배포에서는 전체 학습용 서버를 그대로 노출하지 않고, 필요한 렌더 함수·템플릿을 분리한 비공개 작업자로 사용해야 한다.

자산의 13개 스타일을 모두 옮기지 않는다. 디자이너와 상업 사용이 가능한 독자 템플릿 두 개만 골라 고정한다. 생성 결과의 자유도를 좁히면 작동 여부를 확인할 조합도 줄어든다.

## 3. 8주 범위의 정확한 제품

**누구:** 초대된 대행사 담당자 1명. **대상:** 고객사 브랜드 1개. **한 작업:** 자료를 바탕으로 카드뉴스 6장 또는 8장과 캡션 1개 제작. **편집:** 각 카드 제목·본문·출처, 캡션 직접 수정; 선택한 카드의 문구만 다시 제안받기. **결과:** 확정 버전의 PNG 묶음과 캡션 텍스트.

첫 배포는 고객 한 곳의 전용 작업 공간/인스턴스로 범위를 좁힐 수 있다. 이것도 로그인과 파일 접근 통제를 생략한다는 뜻은 아니다. 두 번째 고객을 받기 전에 인스턴스를 분리하거나, 검증된 조직별 데이터 격리 구조를 갖춘다. 미리 모든 고객이 공유하는 DB를 만들고 나중에 분리하는 선택은 피한다.

레이아웃은 템플릿 안에 고정한다. 사용자는 글·색상 프리셋·미리 등록한 이미지 정도만 조절한다. 초기에는 텍스트 중심 템플릿부터 시작하면 이미지 업로드·잘라내기·저작권 검토 범위를 줄일 수 있다. 사진형이 실제 첫 고객의 필수 요구라면 기본 텍스트형과 교환해서 넣고, 단순히 기능을 추가하지 않는다.

### 화면과 수락조건

| 화면 | 사용자가 하는 일 | 수락조건 |
|---|---|---|
| 초대·로그인 | 발급된 초대로 자기 작업 공간에 접속 | 무권한 요청은 거절. 다른 작업 공간의 파일 주소를 알아도 열리지 않음. 모델 키 입력 요구 없음 |
| 브랜드 자료 | 말투·금지 표현·브랜드 소개, 승인된 문구/기존 원고를 입력 | 자료와 추정 제안을 구분해 보관. URL만 넣으면 내용을 읽었다고 가정하지 않음. 필수 입력은 최소화 |
| 새 작업 | 대상 독자·목적·이번 소재를 넣고 6/8장·템플릿 선택 | 저장 후 다시 열 수 있음. 미완료 상태와 부족한 자료 표시. 첫 시험은 파일 파싱보다 텍스트 붙여넣기 우선 |
| 초안 생성 | 버튼을 눌러 카드별 초안과 캡션을 받음 | 처리/실패/완료가 구분됨. 중복 클릭으로 같은 유료 작업이 중복 실행되지 않음. 실패 시 입력 유지 |
| 템플릿 편집 | 제목·본문·출처·캡션을 폼에서 직접 수정 | 선택한 필드만 변경. 다른 카드 내용 보존. 글자 넘침을 표시하고 내보내기 전에 해결. 변경 후 미리보기 갱신 |
| 부분 AI 수정 | 한 카드에 '짧게/쉽게/다른 제목' 선택 | 원본과 제안을 비교한 뒤 적용. 전체 덱을 덮어쓰지 않음. 미채택 제안은 확정본을 바꾸지 않음 |
| 버전 확정 | 현재 결과를 v1로 확정 | 확정한 덱·캡션·템플릿 버전을 함께 저장. 이후 수정은 v2 초안이 되며 v1 출력 유지 |
| 내보내기 | PNG 일괄 파일과 캡션을 내려받음 | 화면에서 확정한 버전과 파일 일치. 카드 순서·파일명·크기 정상. 재접속 후 다시 받을 수 있음 |
| 내 작업 | 이전 작업을 다시 열고 같은 브랜드로 다음 작업 시작 | 브랜드 자료 재입력 최소화. 초안/확정/실패 상태 구분. 최소한 최근 작업의 연속 사용 가능 |

6/8장이라는 선택까지 불안정하면 첫 고객이 실제 쓰는 한 가지 장수로 줄인다. 화면 수는 논리적 기능 구분이며, 전부 독립 페이지를 만들 필요는 없다. 편집기 한 화면과 작업 목록만으로 합칠 수 있다.

범위에서 제외: 자유 드래그 캔버스, 임의 폰트·도형, 동영상, 자동 트렌드 탐색, 모든 URL/파일의 자동 해석, 동시 공동 편집, 고객사의 다단계 승인, 댓글 스레드, SNS 로그인·발행, 성과 대시보드, 과금 자동화. 결제 실험은 고지된 조건의 수동 청구로 가능하다.

## 4. 36시간 개발 계획과 36시간 검증 계획

| 주 | 학생 개발자: 4.5시간 | 학생 운영·검증: 4.5시간 | 다음 단계 조건 |
|---|---|---|---|
| 1 | 소스 복사·샘플 2건 재현, 사용할 렌더 함수/템플릿 범위 고정 | 대행사 후보·접촉자료 준비, 실제 작업 사례 확보 지원 | 한 실제 작업 입력과 샘플 출력 확보. 자산이 재현되지 않으면 새 기능 착수 보류 |
| 2 | 카드/브랜드/작업 JSON 형식, 고정 샘플로 편집 폼 연결 | 인터뷰/자료 정리, 디자이너와 템플릿 2종·문구 밀도 기준 | 인터뷰에서 실제 반복 업무와 필수 편집 항목 확인 |
| 3 | 기존 원고 생성 연결, 입력 저장, 작업 상태·실패 표시 | 기준 방식의 소요 시간 측정, 브랜드 자료·출처 규칙 정리 | 실자료 3건에서 구조가 깨지지 않고 렌더 가능 |
| 4 | 카드별 폼 편집과 미리보기, 넘침 표시 | 고객 관찰 시험, 말문구/화면 오류 기록 | 고객이 설명 없이 고칠 필드를 찾고 결과를 확인 |
| 5 | 선택 카드 AI 수정, 제안 적용/취소, 버전 저장 | 결과 채택/반려와 보정 시간을 기록 | 운영자 파일 수정 없이 사용자가 부분 수정 완료 |
| 6 | 버전 확정, PNG/캡션 일괄 내보내기, 작업 재열기 | 첫 제한 유료 직접사용, 지원 문의 기록 | 로그인부터 확정본 다운로드까지 한 번 완주 |
| 7 | 새 기능 없이 오류 수정·복구·접근통제 검증 지원 | 동일 고객의 두 번째 실제 작업 관찰 | 첫 작업 때와 다른 자료로 반복 완주 |
| 8 | 잔여 결함 수정·운영 문서·측정 로그 확인 | 재결제 의사보다 실제 재결제/직접사용 확인, 비교 기록 | 다음 고객을 받아도 되는지 별도 결정 |

이 표의 1–6주는 순차 의존성이 있다. 고객 모집이 늦으면 개발자가 예상 고객을 상상하며 기능을 늘리지 않는다. 실제 자료를 확보하지 못한 동안에는 샘플 재현·템플릿 편집·로그 정도만 진행한다. 7–8주는 기능 확장 시간이 아니라 결함·운영의 여유 시간이다.

## 5. 숙련 개발자와 운영 책임자

권고하는 추가 16–24시간은 대략 다음 용도다. 기존의 검증된 계정·저장·작업 실행 골격을 쓸 수 있다는 전제이며, 사용 기술을 처음 배우거나 원본 서버를 대규모 수정해야 하면 늘어난다.

- **1–2주 4–6시간:** 원본에서 가져올 기능 경계 결정, 인증·작업 공간 격리·비공개 결과 저장 구조, 배포 골격. 2주 말까지 이 역할이 없으면 외부 고객 데이터를 받는 개발 범위를 제한한다.
- **3–4주 4–6시간:** 렌더/모델 비밀키를 서버에 두고 작업 시간초과·중복·재시도를 처리하는 연결을 구현하거나 검토한다. 파일 경로·고객 입력으로 내부 파일/임의 주소를 읽는 문제가 없는지 확인한다.
- **5–6주 6–8시간:** 최초 외부 사용 전 로그인/권한/파일 접근/버전/내보내기/복구 시험, 첫 배포, 실패 원인 관측. 이 단계는 출시 전 필요하다.
- **7–8주 2–4시간:** 첫 실제 사용에서 생긴 결함·운영 인계·다음 고객 추가 여부 검토.

추가 인건비는 `합의한 시간당 단가 × 실제 투입 시간`이다. 30만원 실비에 이 개발비가 포함된 것처럼 쓰면 안 된다. 지인의 무상 협력도 사업 원가 평가에서는 투입 시간과 대체 비용을 기록한다.

**운영 책임자는 반드시 한 사람을 지정해야 한다.** 학생 개발자에게 36시간 개발과 별개로 상시 대응 의무가 있다고 가정할 수 없다. 첫 파일럿은 평일 정해진 시간에 문의를 확인하고, 장애 시 재생성/환불/중단 중 무엇을 하는지 고객에게 고지한다. 운영 학생은 문의와 재현 기록, 숙련 개발자는 기술 복구, 사용자는 판매·가격·제품 범위 결정을 맡는다. 디자이너는 템플릿과 결과 품질을 검수한다.

사용자 본인의 고객 접촉·범위 결정 시간과 디자이너의 템플릿 작업은 학생 72시간 밖이다. 고객 접근이 아직 없는 상태에서는 첫 2주의 가장 큰 병목이 코드보다 접촉·실자료 확보일 수 있다.

## 6. 보정 대행업으로 굳지 않게 하는 규칙

1. **사람이 보정하면 숨기지 않는다.** 카드별 수동 보정 시간, 운영자 개입, 고객의 직접 편집을 분리한다. 무료 노동으로 납품을 완성한 사례를 자동화 성공으로 세지 않는다.
2. **기능 수정과 고객별 특별 작업을 구분한다.** 같은 문제가 2–3개 작업에서 반복되면 템플릿/규칙/폼으로 해결한다. 고객 한 곳만 요구하는 맞춤 디자인은 이번 소프트웨어 상품 범위 밖으로 적는다.
3. **편집을 실제 제품 안에서 끝낸다.** 고객이 매번 Canva로 옮기거나 운영자에게 카톡으로 수정 요청해야 하면, 제안한 직접사용 제품의 핵심 가설은 아직 통과하지 못한 것이다. 내보내기는 최종 납품·게시를 위한 기능이다.
4. **두 번째 작업을 더 엄격하게 본다.** 첫 작업은 5–10분 안내할 수 있다. 두 번째 실제 작업은 운영자가 작업물을 만지지 않고 고객이 완료해야 한다. 도움 요청을 받으면 개입 시간에 포함한다.
5. **운영 시간 상한을 정한다.** 예를 들어 고객당 주 30분 이내를 시험 기준으로 잡을 수 있다. 이는 업계 표준이 아니라 우리 팀 자원을 지키기 위한 가설이다. 반복 초과 시 가격을 올리거나 기능/고객 범위를 줄인다.
6. **상품을 분리해 판다.** 사람이 완성해 주는 납품팩과 고객이 직접 만드는 도구 이용권을 같은 가격표·성과표로 묶지 않는다. 어느 쪽을 사고 있는지 고객도 알아야 한다.

## 7. 무엇을 측정하면 SaaS 검증이라고 부를 수 있는가

최소 이벤트: 초안 생성, 직접 필드 수정, 부분 제안 채택/취소, 버전 확정, 내보내기, 다음 작업 시작. 모두 고객/브랜드/작업/버전 ID와 연결한다. 장시간 화면을 열어 둔 시간을 작업 시간으로 세지 말고 관찰 시험이나 명시적 시작/종료 기록으로 보완한다.

핵심 판정은 두 번의 실제 과업이다. ①현재 방식으로 처리한 과업의 전체 소요 시간과 수정 기록을 확보하고 ②우리 제품으로 유사 과업을 두 번 처리한다. 결과 품질·자료 난이도가 다른 과업을 같은 조건이라고 부르지 않는다.

후속 투자 검토용 시험 기준 예시: 운영자 파일 수정 없이 두 번째 작업 완료, 확정본 내보내기 성공, 치명적 사실/브랜드/접근 오류 0건, 기존 대비 총작업 시간 30% 이상 감소, 본인이 정한 가격으로 다음 이용에 실제 결제, 지원·직접비를 차감한 기여이익 양수. **한 고객의 통과는 기술·업무 적합성의 초기 증거이며 PMF가 아니다.** 이후 서로 독립적인 고객 5–10곳으로 확장해 다시 측정한다.

처음 5만원 납품팩을 팔았다는 사실은 그대로 유지하되, 그 금액이 월 소프트웨어 구독료에 대한 지불 의사라는 해석은 하지 않는다. 제품 직접사용 시험을 팔 때는 사용 기간·생성 한도·포함 지원을 함께 제시해야 한다.

## 8. 사업모델을 두 층으로 분리

| 독립 대행사 제품 | Rita |
|---|---|
| 대행사 담당자가 자기 고객의 콘텐츠를 더 적은 시간·수정 부담으로 납품 | 여러 공급자의 에이전트를 선택·사용·비교·거래 |
| 첫 매출은 제한 기간 이용권 또는 유료 파일럿. 직접사용과 서비스형 납품을 구분 | 타 공급자 거래가 실제로 생긴 후 거래 수수료·플랫폼 이용료 검토 |
| 고객 수·반복 결제·채택률·지원 부담·기여이익 측정 | 제3자 공급자 선택/반복 구매·거래 성립·품질 문제·플랫폼 기여 측정 |
| 고객별 브랜드/작업/버전/결과 자료를 보관 | 허용된 실행·결과·비용 요약을 받아 신뢰 기록에 사용 |

우리가 소유한 도구를 Rita에 올려 판 매출에 가상의 Rita 수수료를 또 붙여 두 사업의 성장으로 이중 계산하지 않는다. 외부 공급자와 거래할 때 수수료의 분모는 실제 거래액이며, 모델 호출 원가는 누가 부담하는지 별도 계약한다.

첫 단계 Rita 연결은 어댑터 스펙과 공통 ID를 남기는 것으로 충분하다. `run_id`, `agent_version`, `artifact_version`, 직접비, 수정/확정/내보내기 사건을 기록한다. 범용 게이트웨이·MCP·공급자 정산을 이 제품의 직접사용 조건으로 묶지 않는다.

## 9. 진행·축소·중단 기준

- **2주 말:** 실제 자료를 제공하는 후보가 없으면 제품 범위를 늘리지 않고 모집 제안/채널을 한 번 바꿔 본다. 이것을 곧 시장 전체의 수요 부재라고 단정하지는 않는다.
- **4주 말:** 템플릿 안에서 글을 직접 수정해 볼 수 없거나 초안 구조가 반복해서 깨지면 8주 기능 약속을 줄인다. 색/사진/AI 부분 수정 중 덜 중요한 기능을 제외해 완주를 먼저 만든다.
- **6주 말:** 접근 통제·확정본 일치·작업 복구가 검증되지 않으면 공개 출시·외부 확장을 보류한다. 새 기술이 필요한 상태에서 학생 잔여 9시간으로 해결된다고 가정하지 않는다.
- **8주 말:** 사용자가 직접 두 번째 작업을 끝내지 못하면 SaaS 준비 완료로 부르지 않는다. 특정 고객의 가치가 높으면 고가 서비스로 별도 검토할 수 있으나, 그것은 다른 원가·인력 구조의 사업이다.
- **반복 구매가 없을 때:** 원인이 출력 품질·편집 불편·업무 빈도·가격·기존 도구 전환비용 중 무엇인지 분해한다. 근거 없이 자동 발행과 대시보드를 추가해 해결하려 하지 않는다.

지금 제안할 수 있는 것은 성공 보장이 아니라 **사용자가 실제로 직접 써서 돈을 내는지 확인할 수 있는, 자원에 맞는 제품 실험**이다. 통과하면 그때 자동 발행·복수 브랜드·고객 승인으로 확장한다.

## 10. 부모 작업에서 제시한 구체 예산·가격·일정에 대한 보정

예산 예시 `학생 72시간×2만원=144만원 + 디자이너 5시간×5만원=25만원 + 숙련 개발자 16–24시간×8만원=128–192만원 + 추가 실비 30만원`은 합계 **327–391만원**이다. 모두 합의된 견적이 아닌 계획 가정이며 창업자 시간은 제외된다. 이미 지급 중인 학생비 등으로 추가 현금지출이 달라질 수 있지만 총투입비용에서는 지우지 않는다.

가격 가설은 브랜드 1개 직접사용 30일 59,000원 파일럿, 이후 조건부로 브랜드 3개·30세트 149,000원 본상품이다. 한 세트는 카드 6–8장과 캡션이다. 고객 사진 또는 사용권이 있는 자료를 사용하며 고가 영상·AI 이미지 대량 생성은 제외한다. 직접 텍스트 폼 편집은 생성 횟수에서 차감하지 않고, 부분 AI 수정은 예를 들어 세트당 3회처럼 한도를 시험할 수 있다. 실패한 서버 요청을 정상 고객 수정 횟수로 차감하지 않되 내부 원가에는 기록한다.

59,000원 파일럿은 포함 세트 수가 아직 없으므로 명시해야 가격·원가 평가가 완결된다. 예를 들어 8세트를 시험 한도로 둘 수 있지만 이는 새 제안이며 확정이 아니다. 149,000원/30세트의 세트당 매출은 약 4,967원이므로, 수동 보정과 개별 지원이 빈번하면 생성 API가 싸더라도 사업성이 나빠질 수 있다. 실제 사용량·성공 출력·지원 시간을 모두 측정해야 한다.

**W4 파일럿 시작→W8 갱신**은 위 기본 일정의 W6 완주와 다르다. 이를 목표로 삼으려면 첫 4주에 초대 로그인·브랜드 자료·텍스트 생성·수동 폼 편집·버전 확정·PNG/캡션 내보내기를 집중하고 부분 AI 수정은 W5 이후로 보낸다. 숙련 개발자의 시간을 첫 4주에 더 투입해야 한다. 초기에 써 본 기능이 적더라도 카드마다 운영자가 대신 고쳐 주는 흐름으로 출시일을 맞추지 않는다.

유료 30일은 달력상 W4가 아니라 **핵심 수락조건을 통과해 고객이 실제로 이용 가능한 날**부터 시작한다. 준비 전 선결제를 받지 않는다면 지연 시 '미청구'가 맞고, 이미 받은 금액이 있을 때만 환불 조항을 적용한다. 완주가 W6으로 밀리면 30일 갱신 관찰은 W10 전후로 밀린다. 이 경우 W8 보고는 '갱신 미관찰'이지 실패도 성공도 아니다. 8주라는 일정에 맞춰 반복매출 증거를 만들어 내지 않는다.

본상품 M2–3 전환 역시 한 고객의 갱신만으로 자동 개시하지 않는다. 복수 브랜드 격리·과금/한도·지원 부담·추가 독립 고객의 직접사용을 확인한 뒤 판매 범위를 늘린다.
