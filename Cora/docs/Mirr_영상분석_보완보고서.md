# Mirr 공식 영상으로 보완한 기능·구현 분석

보완일: 2026-09-29. 기존 로그인 화면 조사일: 2026-09-28.

## 이번 조사로 달라진 판단

Mirr의 핵심은 콘텐츠를 한 번 생성하는 데서 끝나지 않는다. **참고 자료 → 편집 가능한 초안 → 사람이 다듬은 기준본 → 재사용 템플릿 → 반복 자동화**가 이어진다. 특히 좋은 기준본을 먼저 만드는 데 시간을 쓰라는 설명이 장시간 웨비나와 최신 튜토리얼에서 반복된다. 우리가 구현할 대상도 생성 버튼뿐 아니라 이 재사용 흐름 전체다.

이것은 자체 모델을 확보해야만 가능한 구조는 아니다. 독립적으로 생성 모델·구조화된 문서·편집기·템플릿 저장·작업 스케줄러를 결합할 수 있다. 다만 원본의 내부 코드·프롬프트·데이터·품질을 그대로 가져오는 것은 아니다. 아래 구현 방식과 테스트는 우리 서비스의 설계 제안이다.

## 확인 범위와 근거의 강도

일반 동영상 탭의 긴 튜토리얼 4편과 라이브 탭의 장시간 강의 2편, 약 190분 분량의 **한국어 자동 생성 자막 전체**를 읽었다. 무음 대기·인사·홍보·반복 Q&A는 기능표에서 제외했다. 모든 영상을 전 구간 시각적으로 시청한 것은 아니다. 자막은 오인식이 있으므로 불명확한 표현을 정확한 버튼명·규격으로 단정하지 않았다. 원문 자막은 작업 자료로만 보관하고 이 문서에는 요약과 타임스탬프를 남겼다.

기존 109개 기능·옵션과 API 83개 작업은 그대로 보존했다. 여기에 기능 단위로 중복을 합친 35개 보완 기록(Y01–Y35)을 연결한다. 35개가 모두 신규 기능은 아니며 109개에 더해 독립 기능 수로 세지 않는다. 영상에서 설명된 동작은 실제 계정에서 직접 실행 검증한 것과 구분한다.

추가로 확인한 6분 52초 라이브(Mu51c0sPIJE)는 자막 추출을 두 번 시도했으나 확보하지 못했다. 같은 제목의 67분 강의와 완전히 중복이라는 판단은 하지 않았다. 23초 데모(FaNP6c7ES3E)와 Shorts 개별 영상의 상세 분석은 이번 긴 영상 중심 조사에 포함하지 않았다. 따라서 채널 전체 영상의 모든 기능을 검증했다는 의미는 아니다.

## 중복을 합친 기준

같은 입력·변환·결과를 설명하면 하나의 기능으로 합치고 여러 영상의 시간을 한 항목에 연결했다. 예를 들어 링크 가져오기는 카드뉴스·영상·URL 전용 튜토리얼에 반복되지만 Y01 하나로 묶었다. 디자인 재사용도 단순 저장과 자동화에 연결하는 동작은 다르므로 Y06·Y21·Y29로 나눴다. 가격과 과거 제한은 기능으로 늘리지 않고 아래 변경·충돌 표로 분리했다.

## 제품 기능으로 채택하지 않은 주장

발표자가 말하는 ‘30배 빠르다’, 매출·조회수 사례, 체류시간의 알고리즘상 중요도, 음악 삽입과 노출의 관계, 계정 초기 조회수 하한, 특정 게시 빈도의 효과는 실측·인과 검증 자료가 아니다. 이런 주장을 우리 제품의 보장이나 고정 알고리즘으로 구현하지 않는다. 이미지·음악·AI 결과물의 권리에 관한 발표자의 단정도 이용 허가의 근거로 쓰지 않는다. 실제 사용 소재의 출처와 이용조건을 별도 관리하는 설계를 제안한다.

## 개발 순서에 반영할 변경

P0는 첫 카드뉴스 제작 흐름의 필수 기반이다. URL/직접 입력→소재 정책→기획 승인→문서 생성→한글·넘침 검사→편집·저장→승인 기준본→템플릿 재사용까지 한 흐름을 완성한다. 단순 생성 데모보다 기준본을 다른 원문에 다시 적용하는 성공을 완료 기준으로 삼는다.

P1에서는 비율 파생본·여러 출력과 영상·블로그를 붙이고, 샘플 검토를 거친 반복 제작으로 연결한다. 자동화는 출력 품질이 안정된 제작기를 재사용해야 한다. P2에서는 계정 연결 후 댓글/DM·실측 성과 분석을 검증한다. 이는 우선순위 제안이며 일정·개발비 추정은 기존 Claude 코드의 상태를 확인한 뒤 산정한다.

## 중복 제거 기능·구현 대장

각 항목의 ‘영상에서 확인’은 자막의 발표 내용이다. ‘우리 구현’과 ‘완료 테스트’는 독립 설계 제안이며 아직 구현·통과하지 않았다.

- 남은 확인: 모든 URL이 된다는 발표 표현을 보장으로 채택하지 않는다. 사이트별 수집 성공률은 별도 검증.

## 구현에 필요한 공통 데이터 구조 — 제안

Source(원문·출처·미디어) → Brief(목표·독자·사실·CTA) → ContentDocument(카드/장면/글) → ApprovedReference(승인 기준본) → TemplateVersion(고정·가변 규칙) → AutomationSpec(소재·일정·전달·검수·예산) → Run(리서치/제작/전달 상태) → Publication(외부 게시물 ID) → MetricsSnapshot(지표·관측시각).

EditEvent에는 원본 버전, 수정 범위, 전후 차이, 사용자 승인 여부를 남긴다. 이 기록이 있어야 다음에 어떤 규칙을 개선할지 판단할 수 있다. 데이터를 저장했다는 것만으로 모델이 학습했다고 표시하지 않는다.
