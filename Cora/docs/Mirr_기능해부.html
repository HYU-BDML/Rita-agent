Mirr 기능 해부와 노하우 분석

화면·API 조사일: 2026-09-28. 공식 영상 자막 보완일: 2026-09-29. 대상: https://www.mirra.my/ . 사용자가 로그인한 체험 계정의 화면, 공개 소개·도움말·가격·정책 페이지, 공개 고객 API 명세를 함께 확인했다.

먼저 답하면

같은 역할을 하는 서비스는 만들 수 있다. 어려운 부분은 생성 버튼 자체보다, 원문을 잘 이해하고 브랜드 스타일을 지키며 편집 가능한 결과를 안정적으로 만드는 작업이다. Mirr의 공개 자료만으로 독점 학습 데이터나 자체 모델의 우위를 입증할 수는 없다. 반면 실제 화면과 명세에서 디자인 템플릿, 문체 참고 자료, 계정 지식자료, 영상의 시간·레이아웃 규칙, 중복 실행 방지 등 구현 노하우가 필요한 구조는 확인된다.

이 문서는 제품을 만든 결과물이 아니라 기능 조사 결과다. 기능별로 화면에서 확인했는지, API 문서에서 확인했는지, 공식 소개에만 있는지를 구분한다. 기능의 존재와 기능의 품질을 구분하며, 구현 제안은 원본 내부 구현으로 단정하지 않는다.

조사 범위와 정확한 한계

공개 URL 71개를 수집했다. 여기에는 중복 용도의 소개 페이지와 로그인으로 이동하는 URL도 포함되므로 71개가 서로 다른 기능을 뜻하지 않는다. 로그인 뒤 생성·기획·자동화·캘린더·댓글·DM·분석·링크 페이지·계정·팀·구독·API 화면을 열고 입력 옵션과 템플릿 편집기를 조사했다. 공개 OpenAPI에는 HTTP 메서드와 경로 조합 기준 83개 작업이 있다. REST 작업과 화면 기능은 겹치므로 두 개수를 합산하지 않는다.

체험 계정은 SNS가 연결되지 않았고 생성 이력이 없었다. 따라서 실제 SNS 발행·댓글·DM 수신과 송신·실측 분석은 검증하지 못했다. 음성 복제는 Launch 이상 제한을 확인했다. AI 생성·크레딧 차감·렌더링·다운로드의 실제 성공률, 유료 구독·자동충전·정산은 실행 검증하지 않았다. 기본 템플릿의 편집 도구는 열었지만 원문 수정이나 저장을 실행하지 않았다. 모션그래픽의 다음 입력 단계를 보기 위해 비민감한 예시 대본만 입력했으며 생성은 시작하지 않았다.

‘모든 기능을 완전히 테스트했다’는 결론은 아니다. 현재 접근할 수 있는 기능 표면을 최대한 펼치고, 막힌 영역과 미검증 동작을 명시한 조사다. 숨겨진 운영자 기능·실험 기능·기업 계약별 기능까지 완전성을 보장할 수 없다.

제품을 구성하는 실제 흐름

입력 자료 → 계정·브랜드 맥락 → 아이디어·참고 조사 → 카드뉴스/영상/블로그/텍스트 → 검토·편집 → 다운로드 또는 예약 발행 → 댓글·DM·성과 → 다음 기획.

그 주위에 워크스페이스·팀 권한·SNS 연결·미디어 자산·크레딧·알림·API/MCP가 붙는다. 이를 자신의 서비스로 만들려면 생성기 여러 개뿐 아니라, 각 단계의 결과와 실패 상태를 이어주는 데이터 구조가 필요하다. 이는 조사 결과를 바탕으로 한 설계 판단이다.

카드뉴스: 무엇을 만들어 저장하는가

실제 첫 화면은 AI가 디자인을 골라주는 빠른 생성과 템플릿 직접 선택을 나눈다. 주제·대본·링크·사용자 미디어, 출력 언어와 비율을 받고, 고급 옵션에서 장수·검색·기획 검토를 설정한다. 별도의 Learn 화면에서는 참고 이미지 또는 공개 Instagram 게시물에서 디자인을 학습하고 반복 사용한다.

기본 템플릿을 열어보니 예시 이미지와 실제 디자인 구조가 구분돼 있었다. 조사한 템플릿에는 6개 페이지가 있고, 각 페이지에서 텍스트와 이미지를 개별 레이어로 선택할 수 있었다. 서체, 크기, 색, 두께, 정렬, 자간·행간, 이미지 모서리·투명도, 요소 순서, 복제, Undo/Redo, AI Designer가 제공된다. 원본 기본 템플릿을 편집하면 개인 템플릿을 만드는 흐름이다.

이 구조를 재현하려면 완성된 이미지만 저장해서는 부족하다. 페이지·요소·스타일·원문을 분리해 저장하고 화면과 이미지 내보내기에서 일관되게 렌더링하는 방식이 필요하다. 긴 한글 문장, 다른 서체, 여러 비율에서 줄바꿈과 넘침을 검증하는 부분이 노하우가 쌓일 지점이다. Mirr의 정확한 템플릿 생성 프롬프트와 배치 알고리즘은 공개하지 않았다.

근거: 카드뉴스 제작기, 디자인 학습.

영상: 대본 작성과 MP4 제작은 별도 단계다

일반 영상은 주제/대본 입력, 대본 재작성/원문 유지, 언어, 비율, 목소리, 길이, 음악, 자막 강조를 설정한다. 템플릿 기반 영상과 모션그래픽 제작도 따로 있다. 일반 영상 길이 UI는 1–150초이며, 실제 길이는 달라질 수 있다고 안내한다.

API 명세는 더 구체적이다. 검토용 대본·장면 초안을 만든 뒤, 확정 단계에서 음성과 소재 처리를 수행하고, 별도 렌더 단계에서 MP4를 만든다. 결과 문서에는 장면·자산·위치·시간·트랙·음성·테마·전환이 들어간다. 각 장면에는 hook/body/cta 역할, 길이 정책, 미디어 후보와 선택 상태가 있다. 따라서 영상 생성은 한 번의 텍스트 응답이 아니라, 구조화된 문서를 만들고 여러 작업을 거쳐 출력하는 과정이다.

특히 말이 장면보다 길어질 때 속도 증가·대본 축약·장면 연장 중 처리 방식을 지정하는 필드가 있다. 최신 문서 시각이나 fingerprint를 확인하는 입력도 있어, 사용자가 편집한 내용을 오래된 AI 수정이 덮어쓰지 않도록 설계할 수 있는 구조다. 이런 규칙의 존재는 확인했지만, 실제 선택 알고리즘과 품질은 확인하지 못했다.

상태가 completed이고 출력 URL이 있어야 완성본으로 사용해야 한다. 저장된 영상은 백그라운드 렌더링을 요청하고 상태를 조회하도록 문서에 명시한다. 단순히 요청이 성공했다는 이유로 다운로드 가능한 영상이 완성됐다고 표시하면 안 된다.

근거: 영상 제작기, API 문서.

블로그: 조사·개요·본문·SEO를 분리한다

작성 화면에서 톤, 독자, 목표 길이, 키워드, 참고 URL, 추가 지시, 요약·FAQ·팁, CTA를 설정한다. My Styles에서는 최소 두 개의 참고 글로 문체 분석을 시작하도록 안내한다. 이는 브랜드 말투를 기억시키는 제품 경로이며, 신경망 가중치를 다시 학습한다는 증거는 아니다.

API의 진행 상태는 researching→outlining→outline_review→writing→seo_optimizing→generating_image→draft/completed로 나뉜다. 개요 검토에서 사용자가 섹션을 승인하면 본문 작성이 시작된다. 동일한 개요를 다시 승인해도 새 작업을 중복으로 배포하지 않으며, 상태가 맞지 않거나 충돌하면 409를 반환한다고 명시돼 있다. 조사 출처, 섹션별 이미지 후보, 메타 제목·설명·키워드와 공유 이미지도 구조화한다.

같은 기능을 만들 때는 초안 품질뿐 아니라 작업 중 새로고침, 중복 클릭, 수정한 목차와 이전 목차의 충돌을 처리해야 한다. 공식 API 문서는 WordPress 발행을 제공하지 않는다고 명시한다.

근거: 블로그 작성, API 문서.

댓글·DM: 생성, 승인, 송신, 기록을 구분해야 한다

댓글 관리 화면은 계정·기간·정렬·미응답 수로 대상을 고른다. API는 답변 생성과 단건·일괄 전송을 구분한다. 별도로 조회 수 임계값 또는 발행 후 경과 시간에 따른 후속 댓글을 정의할 수 있다. CTA 문구를 저장하고 재사용하는 API도 존재한다.

DM 자동화는 계정/게시물→키워드→메시지의 세 단계다. 우측에는 고객과의 대화 미리보기가 나타난다. 공식 소개는 공개 답글+DM 동시 전송, 키워드별 다른 메시지, FAQ 자동 답변을 설명한다. 실제 실행 기록 화면은 발동·전송·실패 건수와 대기/실패 상태를 구분한다.

우리 서비스의 구현에서는 같은 댓글 이벤트가 두 번 도착했을 때 두 번 보내지 않는 처리, 여러 키워드에 동시에 해당할 때의 우선순위, 만료된 계정 권한, 전송 제한, 재시도를 설계해야 한다. 이는 독립 구현에 필요한 항목이며 Mirr가 어떤 구체적 방법을 쓰는지는 공개되지 않았다.

근거: 댓글 관리, DM 자동화, API 문서.

데이터가 ‘노하우’가 되는 지점

계정 지식자료는 업로드 주소 발급→문서 처리→지식자료 조회→기획에서 특정 자료 선택으로 이어지는 API 구조가 있다. 스타일은 참고 글이나 디자인에서 저장해 재사용한다. 계정 설정은 독자·콘셉트·문체·글 길이·참고 게시물·발행 시간을 보관한다. 성과 데이터는 게시물 ID, 계정, 발행 시각, 노출 지표의 종류, 반응과 갱신 시각을 연결한다.

여기까지는 확인된 제품 구조다. 이 데이터로 실제로 어떤 추천 모델을 학습하는지, 고객 간 데이터를 섞는지, 수동 검수 사례를 얼마나 축적했는지는 확인할 수 없다. 홈페이지 누적 조회 수나 연결 게시물 수를 ‘학습 데이터 규모’로 바꾸어 말해서는 안 된다.

독립적으로 만들 때는 원문→초안→사용자 수정→승인본→발행 결과를 연결해 저장하는 것이 유용하다. 예컨대 같은 유형의 카드에서 사용자가 계속 글을 줄이면 텍스트 길이와 레이아웃의 관계를 개선할 수 있다. 성과가 높다고 곧바로 후크가 좋았다고 학습하지 말고 계정 크기·관측 기간·광고 여부도 구분해야 한다. 이는 우리 서비스의 설계 제안이다.

근거: 공개 API 명세, 계정 맥락 활용 설명.

경험이 품질로 바뀌려면

데이터가 많다고 자동으로 노하우가 되지 않는다. 원문, 최초 초안, 수정본, 최종 승인본, 사용한 모델·프롬프트·템플릿 버전, 생성 비용, 게시물 ID, 발행 시각, 반응을 서로 연결해야 한다. 그래야 실패가 어느 단계에서 생겼는지, 사용자가 무엇을 고쳤는지, 어떤 수정이 반복되는지를 확인할 수 있다.

예를 들어 한 카드의 문장을 사용자가 세 번 줄였다면 단순히 최종 문장만 저장하면 부족하다. 최초 글자 수, 레이아웃의 텍스트 영역, 실제 줄 수, 수정 이유를 저장하면 다음 생성에서 해당 유형의 카드에 더 짧은 문장을 배치하는 규칙을 만들 수 있다. 이 규칙은 다른 문장·서체·화면 크기에서도 검증해야 한다.

반응 데이터도 마찬가지다. 조회수가 높은 게시물 하나만 보고 후크가 좋았다고 학습하면 계정 규모, 광고 집행, 계절 효과를 혼동할 수 있다. 같은 계정에서 비슷한 관측 기간을 사용하고, 저장률·완독률·문의 전환 등 목적에 맞는 지표를 따로 보아야 한다. 이는 우리 서비스 설계 제안이며 Mirr가 실제 이렇게 운영한다는 뜻은 아니다.
