## 3. 기능을 줄이는 방법

1. 고객사 공간: 반복 주제·말투·시각 규칙·금지 표현·자료·연결 계정·검토자.

## 4. 고객의 사용 흐름과 화면별 완료 기준

## 5. 가장 중요한 차별성: 수정할수록 계정에 맞는 결과

현재의 규칙 기반 광고 검사는 시작점이다. 입력 사실에 없는 숫자를 찾는 것이 모든 거짓 주장 검출은 아니고, 계정 주제 단어가 있다고 맥락이 맞는 것도 아니다. 실제 표현·시각·주제의 적합성을 사람이 평가해야 한다.

### 고객사 기억의 데이터

- ClientProfile: clientId, workspaceId, 설명, 타깃, 주제, 말투, 금지어, 시각규칙, 이미지 참고, 담당자.
- SourceEvidence: 원문/이미지 식별자, 출처, 관측시각, 이용권한 메모, 사용 목적, 삭제 상태.
- BrandRule: 규칙, 근거 자료/수정기록, 제안자, 확인자, 적용범위, 만료, 버전, 활성/철회.
- WeekPlan: 주차, 목표, 후보, 선택 이유, 작업물/담당자/기한 관계.
- ContentRevision: 불변 스냅샷, 저장자, 부모 버전, 사용 규칙 버전, 미디어 해시.
- ReviewDecision: 검토자, 대상 revision, 코멘트 위치, 승인/수정요청/철회, 시각.
- PublicationJob: 실제 소유 accountId, 승인 revision/hash, 실행시각, 제출ID, 상태, 재시도 정책.
- PerformanceObservation: 계정/게시물/지표/값/지원여부/수집시각/게시 경과일/유료 여부.

### 기억을 적용하는 규칙

“이번 할인 행사에는 느낌표를 빼 주세요”를 모든 캠페인의 영구 규칙으로 자동 등록하지 않는다. AI가 규칙 후보를 만들고 담당자가 계정 전체/캠페인 한정/이번 콘텐츠 한정 중 선택한다. 외부 검토자의 댓글 자체는 시스템 지시가 아니라 자료다. 소유자나 권한 있는 편집자가 확인한 규칙만 다음 제작에 적용한다.

같은 고객사·현재 유효한 규칙만 조회하고 prompt에 규칙ID/버전을 기록한다. 규칙이 많으면 우선순위와 최근 승인 근거로 골라 넣으며 서로 모순되는 경우 사람에게 선택을 요청한다. 삭제·권한 회수·규칙 철회 이후 생성에 재사용되지 않는지 시험한다. 이를 “모델이 학습됐다”거나 “성과가 보장된다”고 표현하지 않는다.

시각 검토 초판은 고객 승인 템플릿·색·서체·이미지 방식 및 기존 피드 나란히 보기다. 비전 모델로 이미지 설명을 추출하는 후속 확장은 모델 비용·인물/권리·검수 품질을 확인한 뒤 추가한다. 브랜드 시각 규칙이 상품 정보를 읽기 어렵게 만들면 가독성과 필수 사실을 우선하고 수정 근거를 보여준다.

## 8. Codex와 Claude가 검수하는 방식

작업자는 실제 코드와 시험을 만들고, 다른 도구는 공동 인계와 고정 commit에서 독립 재현한다. 역할은 교대 가능하다. Claude가 아직 검수하지 않은 결과를 Claude 통과로 기록하지 않는다. 이 문서 작성 중 Claude에게 메시지를 보내거나 실행시키지 않았다.

검수 층:

1. 계약·단위: 데이터 검증, 역할, 버전, 비용 상태, provider 응답, 날짜·결측.
2. API 부정시험: 다른 고객사 ID·세션없음·철회 권한·잘못된 origin·차단기능 직접 호출.
3. 브라우저: 신규 사용, 고객사 전환, 모바일 검토, 저장실패, 이전 승인, 다음 주 재사용.
4. 산출물: PNG 실제 크기·한글·잘림, JSON 복원, 캡션/이미지/승인 snapshot 일치.
5. 외부 계약: mock과 별도의 실연결 증거. OAuth 거부·토큰 만료·응답유실·429 포함.
6. 운영: 강제종료·재시작·디스크부족·백업 복구·rollback·권한회수 후 job.
7. 사람: 계정 분위기·읽기 편함·사실 적합성·승인 가능성·능동작업시간.

`04_출시시험표.csv`에 65개 시나리오를 준비했다. 각 행은 실행 commit, 환경, 입력 fixture 버전, 기대/실제 결과, 증거파일, 검수자를 기록한다. 캡처만으로 권한/게시를 통과시키지 않으며 단위시험만으로 시각 품질을 통과시키지 않는다.

모든 구현 작업의 종료 조건: 대상 코드와 source provenance, 관련 회귀 시험 통과, UI 변경 시 브라우저/모바일 검수, 미검증 외부 상태 표시, 비용 제한, 백로그/인계 갱신, 본인 변경만 commit, 같은 branch push, PR 최신 설명. 문제가 없는데 전체 시험을 반복 소모하지 않는다. 공통모델/권한/배포 변경 후와 출시후보 고정 시 전체 회귀를 수행한다.

## 9. 실제 콘텐츠 품질과 경쟁 비교

고정 평가자료 12세트: 교육/전문지식·로컬 서비스·소형 소비재의 3업종 × 서로 다른 스타일2개 × 정보성/광고 브리프2개. 사용자 동의 자료 또는 명백한 가상 자료로 준비하고 정답 사실·금지표현·참고 이미지·타깃·승인 기준을 기록한다. 개인정보와 고객 원자료는 Git에 넣지 않는다. 자동 테스트는 익명화 fixture만 쓴다.

라이브 AI는 처음 3호출 이내로 광고/일반 생성 샘플을 검수하고 나머지는 미실행으로 둔다. 캐시 결과로 UI·저장 회귀를 검수하며 품질 평가용 서로 다른 입력은 따로 계산한다. 한도를 회피하려고 호출을 잘게 쪼개지 않는다. 이후 평가 확대는 기존 비용 정책과 사용자 예산 안에서 수행한다. quality 모드는 사용자가 선택할 때만 사용한다.

평가표: 사실 오류(0/있음), 계정 적합성(1~5), 읽기·시각품질(1~5), 목표/CTA 적합성(1~5), 재사용 복사 여부, 수정한 카드 수, 승인가능/수정필요, 수정분. 출시 목표 초안은 중대한 사실 오류0, 12세트 중9세트가 작은 수정 후 승인가능, 중간 계정적합성4/5 이상이다. 작은 표본의 내부 판단 기준이며 통계적으로 우수한 제품이라는 광고 근거가 아니다. 기준은 첫 평가 전에 고정하고 실패 후 몰래 낮추지 않는다.

경쟁 비교는 고객이 실제 쓰는 방식과 Cora를 같은 자료/납품기준으로 비교한다. Mirr 접근권한이 있으면 같은 조건의 비교군으로 넣고 없으면 미비교로 표시한다. 도구 순서를 바꿔 학습효과를 줄이고 평가자에게 가능하면 제작 도구명을 가린다. 대행사 담당자의 입력·수정·자료찾기·검토준비 등 능동시간과 AI/고객 응답 대기시간을 분리한다. 고객사1개 과제만 빨라졌다는 이유로 다중고객 업무까지 검증했다고 하지 않는다.

## 10. 데이터·운영 아키텍처

초기 운영 목표는 초대 사용자50명 이내·고객사25개 이내·동시 사용10세션이다. 이는 설계/부하 시험 범위이며 상용 SLA가 아니다. 단일 app/worker와 영구 디스크 SQLite로 시작할 수 있지만 다중 서버 쓰기를 허용하지 않는다. 테스트에서 한계가 확인되거나 확장 요구가 생길 때 Postgres/공유 queue로 이전한다. 분산 인증 제한과 작업 claim은 배포 구조에 맞게 공용 DB 등에 저장한다.

필수 구성: Cora 전용 배포명세, 검증된 Node/Python/llmgw 버전·모델 routing, 비밀 환경 설정, app↔worker 건강상태, 원자적 schema migration, DB와 게시미디어 영구저장, HTTPS origin/callback, 제한된 외부 미디어URL, 외부 모니터링 및 생성·게시 kill switch. Drive 폴더는 소스/문서 협업 위치이며 고객 운영 DB 서버가 아니다.

저장 이전과 백업은 SQLite WAL까지 일관성을 보장하는 방법으로 수행한다. 목표 RPO24시간/RTO4시간을 새 환경 복원으로 실측하고, DB만 복원해 media가 없는 상태를 성공으로 처리하지 않는다. 암호화키는 DB와 분리 보관하며 키가 없을 때 OAuth 재연결 복구 절차를 기록한다. 삭제된 고객자료가 백업 복원으로 되살아나는 문제를 삭제 tombstone/재삭제 절차로 방지한다. 보관 기간은 실제 운영정책과 맞춘다.

현재 `render.yaml`은 과거 Trend 시연용이다. Cora 고객 DB를 커밋하거나 휘발 파일시스템에 저장하는 방식으로 배포하지 않는다. 이번 의존성 audit high1/moderate1은 재현·노출 검토와 호환성 시험을 포함한 L38에서 처리한다. 자동 `npm audit fix --force`로 대형 버전 변경하지 않는다.

## 11. Instagram과 외부 설정

첫 플랫폼은 공식 Instagram API 경로를 우선한다. Blotato는 대안 코드로 보존하되 새 구독을 기본 전제로 삼지 않는다. 읽기 연결부터 검증하고 게시가 필요할 때 권한을 확장한다. 요청 scope와 실제 허용 결과를 구별한다.

필요 입력: 안정적인 HTTPS 접속주소/복귀주소, Meta 앱 서버 비밀값을 Git·채팅 밖에 저장, 전용 시험 Instagram 전문가 계정, 미디어 저장소 접근권한, 사용자 직접 OAuth 승인. `bdm.lab`은 사용자가 운영하는 계정이므로 자료 읽기는 허용 범위에서 진행하되 첫 게시 시험 계정으로 자동 간주하지 않는다. 비밀번호를 받을 필요가 없다.

실제 게시 시험은 플랫폼별 첫 게시 시 사용자 확인을 받아 전용 시험계정에 승인한 내용만 올린다는 기존 지시를 유지한다. 승인/준비 전 실제 게시·외부 메시지·구독·결제는 실행하지 않는다. 필요한 설정의 존재 여부만 출력하고 secret은 출력하지 않는다.

## 12. 사업모델·예산·검증

가격 단위는 활성 고객사 수를 기준으로 구독을 제안하고, 생성/보관 한도로 고비용 사용을 제어한다. 시트수/크레딧/영상분량 등 여러 요금축을 처음부터 고객에게 동시에 이해시키지 않는다. 담당자·검토자는 협업에 필요한 범위에서 포함하고 고비용 생성/저장만 별도 상한을 둔다.

가격은 아직 결정하지 않았다. 예를 들어 3고객사 월9.9만원과 10고객사 월24.9만원을 인터뷰 카드로 비교할 수 있다. 이는 시장조사로 입증한 가격/할인 약속이 아닌 검증안이다. 생성 한도·지원비용·부가세/청구 조건 확정 전 판매하지 않는다. 무료 체험은 고객사1개·주간 묶음1회 등 실제 가치 확인까지로 설계하고 무제한 생성은 제공하지 않는다.

경제성 식: 월 기여이익 = 수금액 − AI/API − 저장/트래픽 − 결제비 − 가변 지원시간×시간단가. 초기에는 고객별 실측이 필요하며 cost=null 상태에서 원가가 낮다고 주장하지 않는다. 높은 생성량·재생성률·지원부담 고객을 포함한 보수적 시나리오를 작성한다. 기여이익률60% 이상, 사용량이 커져도 적자 방지 가능한지 검증 목표로 둔다. CAC 회수기간/LTV는 실제 반복수금/이탈 자료가 부족하면 산출하지 않는다.

예산 제안은 승인된 지출이 아니다. 첫 hosted 파일럿의 월 총한도는 10만~30만원 범위로 검토하고, 실제 hosting·저장소·메일·AI 견적을 확인해 확정한다. 사람 시간과 개발자 검토비는 이 범위 밖이다. 예산 미정이면 local/mock 작업을 계속하고 결제·유료 subscription은 생성하지 않는다. 고객 수요 확인 전 광고집행비를 배정하지 않는다.

### 사업 검증의 진행/수정/중단 기준

- 진행: 대행사3곳 중2곳이 다음 주에도 사용, 승인 콘텐츠당 능동시간 중앙값30% 이상 절약, 품질 저하 없음, 2곳 이상 실제 유료전환 또는 유료계약. 목표 수치이며 아직 결과 없음.
- 수정: 결과물은 좋아하지만 검토자 참여가 어렵다 → 검토 UX 개선. 생성은 쓰지만 승인/운영을 안 쓴다 → 고객군/약속 재점검. 원가·지원비가 높다 → 한도/가격/자동화 개선.
- 대량투자 보류: 적절한 고객3곳의 두 번 운영주기를 관찰하고 두 차례 핵심 개선 후에도 반복 사용·지불이 없음. 이것만으로 시장 전체가 없다고 결론내리지 않되 같은 제품의 기능만 늘리지 않는다.
- 비교 우위가 릴스·DM 등 현재 보존 기능에 달렸다는 일관된 증거가 나오면 재우선순위. 우연한 한 요청으로 전체를 다시 펼치지 않는다.

## 14. 파일·상태·협업 운영

기준 폴더는 사용자가 지정한 Drive의 `조유경(소셜미디어)/work/rita-agent-source/Cora`이며 다른 원본 checkout을 만들지 않는다. 문서는 Cora/docs에서 버전관리하고 outputs/Cora_출시집중_2026-10-04로 복사한다. 원래 outputs/work symlink를 유지한다.

기능 원장119행은 장기 목표, 출시 범위표는 공개 지원할 부분, 실행백로그는 만들어야 할 단위, 시험표는 완료 증거다. 네 표를 혼동하지 않는다. 새 주간묶음/수정기억/게스트검토는 L번호로 추적한다. 광고 제작은 F008 광고검색을 대체 완료하지 않는다.

작업 상태: 미착수 → 구현중 → 로컬검증 → 독립검증 → 실환경검증 → 출시포함. 외부설정대기/외부심사대기는 별도 차단 사유로 적으며 완료가 아니다. 이 문서의 L01 완료는 범위 문서 완성이며 기능 완성이 아니다.

결함 표 최소 필드: ID, 심각도, 발견 commit, 환경, 재현 단계, 기대/실제, 영향 고객/계정 범위, 증거, 수정 commit, 회귀 시험, 독립 재검수자, 잔여 위험. 코멘트로만 “고침”이라 쓰지 않는다.

## 15. 공개 직전 준비 완료의 정의

같은 출시 후보 commit에 대해 핵심 업무 E2E·모바일·접근제어·모의 장애·실제 연동·PNG 품질·백업복원·부하·비용·정책/안내·지원 준비 증거를 연결한다. 미실행 시험을 pass로 바꾸지 않는다. 제외 기능은 접근차단·의존성 검수까지 한다. 무료 내부 데모, 초대 파일럿, 공개 자동운영, 유료 확장은 각각 따로 승인한다.

최종 검토 자료: 실제 지원 기능표, 알려진 제한, 남은 P2, 외부 허용상태, 시험계정 게시 URL 증거, 운영 예산 상한, 고객 원가 실측, 첫 고객 사용 기록, rollback 명령/복구시간, 운영담당, 출시 카피. 교수에게는 이 구체적인 결과를 보여주고 공개 여부만 결정하도록 한다.

현재 단계는 이 계획과 기준점 검수까지 완료다. 다음 작업은 L02/L03/L05를 시작하고 작은 단위마다 교차 검수를 연결하는 것이다.
