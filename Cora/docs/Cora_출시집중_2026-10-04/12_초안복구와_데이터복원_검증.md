## 사용할 수 있는 것

1. 제작 전 입력 자료와 카드 초안(문구·사진 data URL·캡션·디자인·고객사 ID)을 편집 후 800ms에 서버 복구함에 보관한다. `지금 초안 보관`으로 즉시 확인할 수도 있다. “복구용 초안 보관됨”은 마지막 입력까지 서버가 확인했을 때만 표시한다. 고객 자료를 localStorage/sessionStorage에 넣지 않는다.
2. 새로고침·재접속 후 `복구 가능한 초안`에서 선택해 불러온다. 원래 저장본으로 이어 편집하거나 카드의 `새 사본으로 복구`를 선택한다. 자동으로 정식 저장/승인/게시하지 않는다. 복구하는 카드의 작업 상태는 작성 중이며 승인 이력을 가져오지 않는다.
3. 원본 저장본이 바뀌면 복구본의 기존 base version을 유지한다. 저장 시409로 덮어쓰기를 막고 사본으로 이어갈 수 있다. 여러 탭은 별도 복구 ID를 사용한다. 동일 ID의 변경/폐기는 CAS 버전을 요구하고, 폐기한 ID는 tombstone으로 남겨 지연된 쓰기로 재생성하지 못한다.
4. 정식 저장 실패에도 복구용 보관본은 유지된다. 저장 중 추가로 입력한 내용도 편집기에 남아 다시 보관된다. 저장한 현재 초안 및 동일 복구 작업의 원본은 정리하며 다른 작업의 보관본은 지우지 않는다. 로그아웃/작업 전환 전 보관 확인이 실패하면 오류를 보여준다.
5. 복구함의 목록·본문·새 보관·계정 내보내기에서 현재 사용자와 고객사 편집 권한을 다시 검사한다. 회수된 편집 권한으로 이전 내용을 복구/내보낼 수 없다. 브라우저의 이전 로그인 actorId 요청은409이며 사용자 전환 시 실행취소 이력/검토 이메일을 초기화한다.
6. DB 백업은 SQLite `VACUUM INTO`로 실행 중 committed WAL까지 일관된 사본을 만든다. 복원은 존재하지 않는 새 폴더에서만 한다. SHA256·행 해시/행수·integrity_check·foreign_key_check·기존 행 보존·이전 두 번 실행을 모두 확인한 뒤 폴더를 게시한다. 기존 폴더는 덮어쓰지 않는다. 부분 실패는 staging 사본만 정리한다.
7. core/client/team/Instagram/계정지정/recovery의 추가 스키마 작업은 DDL+기록을 같은 트랜잭션으로 실행한다. 구버전의 이름 기반 권한은 legacy로 유지하고 새 clientId grant를 추정하지 않는다. 구 Instagram 연결의 scopes도 unknown을 유지한다. 옛/새 토큰 행이 다르면 이전을 중단하고 원본 행을 남긴다.

## 범위와 한계

- 복구 가능 기간30일, 계정당 활성 초안30개·총30MB, 초안당2.9MB. 상한 초과 시 기존 초안을 조용히 지우지 않고 오류를 표시한다. 만료된 초안은 조회되지 않으며 다음 보관 요청에서 본문을 지우고 tombstone만 남긴다. 자동 정기 삭제 job을 이번에 추가한 것은 아니다. SQL 백업에는 만료 전후의 저장 행도 포함될 수 있다.
- 마지막 보관 완료 **이전**에 탭/전원을 즉시 닫거나 네트워크가 끊기면 그 마지막 입력은 보장하지 않는다. beforeunload 경고·보관 상태·수동 보관을 제공한다. 이 변경은 제작 브리프/카드 편집기이며 별도 광고 입력 폼·자산·영상의 모든 미저장 입력까지 포함하지 않는다.
- 이 도구는 **DB만** 백업/복원한다. DB 내 카드 사진 data URL은 포함된다. uploads/media/video 파일, 외부 서비스 자료와 환경 변수·암호화키는 따로 관리해야 한다. DB 복원만으로 전체 서비스 장애복구가 끝난다고 주장하지 않는다.
- 백업 파일은 로그인 hash·세션·암호화된 토큰·자료를 포함하므로 공개 다운로드 API를 만들지 않았다. 디렉터리0700/파일0600인 운영자용 사본이다. Git/공유 outputs에 넣지 않는다. manifest는 행 내용 대신 해시/열명/행수만 포함한다. 체크섬은 손상 검사이며 원본 진위 서명은 아니다.
- 실제 검수 runtime은 Node24.14.0. 선언된 최저22.13.0와 실제 배포환경의 호환성/영구 DB·media 경로·복원 후 전환은 L27/L28 staging에서 별도 검수한다.
