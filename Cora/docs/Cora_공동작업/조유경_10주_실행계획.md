## A. 전체 그림

### A1. Cora가 누구의 어떤 문제를 푸는가

Cora(Content Operations Run by Agents)는 여러 브랜드의 SNS 콘텐츠를 정기적으로 만드는 소규모 광고·콘텐츠 대행사를 첫 고객으로 삼는다. 개인 계정을 키우려는 크리에이터는 후속 후보이며, 이 10주 동안은 대행사의 작업 흐름을 우선한다. Cora가 줄이려는 것은 글이나 이미지를 한 번 만드는 시간이 아니라, 브랜드 자료 파악부터 진단·소재 탐색·기획·카드뉴스와 글과 영상 제작·고객 검토와 승인·게시 준비와 예약·성과 확인·다음 제작 개선까지 브랜드마다 반복되는 전체 작업 시간과 수정 부담, 고객사 관리 부담이다.

### A2. 고객의 현재 방식과 Cora 사용 뒤 기대하는 변화

대행사 담당자 한 사람이 브랜드 3~5개를 맡으면 브랜드별로 자료를 카카오톡·이메일로 받고, 캔바나 미리캔버스로 카드뉴스를 만든다. 고객사 확인은 메신저로 받고 수정 요청을 두세 번 반영한 뒤, 각 SNS에 직접 올리고 월말에 성과를 캡처해 보고서를 만든다. 이 서술은 사용자 제공 자료와 벤치마크 분석에 근거한 가설이며, 10주 안에 실제 대행사 관찰로 확인해야 한다. Cora를 쓰면 브랜드별 자료·말투·검토자가 한 곳에 저장되고, AI 초안을 편집기에서 바로 고치고, 검토자가 저장 버전을 승인하고, 승인본만 게시 준비 큐에 들어가며, 성과 CSV가 다음 제작 기획으로 이어지는 것을 기대한다. 이 기대는 확인할 가설이다. 10주가 끝났을 때 "브랜드 1개의 카드뉴스 1건을 자료 입력에서 승인·게시 준비까지 끝내는 데 걸린 시간과 수정 회차"를 기존 방식과 나란히 기록한 표가 있어야 한다.

### A5. 10주 뒤에 실제로 보여줄 것

1. 가상 대행사 1곳(브랜드 3개)의 4주치 콘텐츠 운영 기록: 카드뉴스 12건 이상, 블로그 4건 이상, 대본 4건 이상을 Cora에서 만들고 검토·승인·게시 준비·모의 큐까지 통과한 기록과 산출물 파일.
2. 제작 1건당 소요 시간과 수정 회차를 1주차·4주차·8주차에 같은 조건으로 잰 표.
3. 외부 대행사 또는 크리에이터 1~2명의 실제 작업 관찰 기록(확보 못 하면 동료 학생 2명 대체 관찰 기록)과 그들이 Cora 결과물을 실제로 썼는지 여부.
4. 조유경이 직접 만들어 교수 저장소에 반영된 수정 파일(패치) 4건 이상(문구·입력 검증·작은 기능).
5. 개발자 검토가 필요한 항목의 구체 목록(F5 양식)과 재현 가능한 버그 보고.

### A6. 유료 파일럿 가능성을 무엇으로 판단하는가

성공을 보장하지 않는다. 다음 세 가설을 관찰로 확인한다. ① 대행사 담당자가 카드뉴스 1건을 Cora로 만들면 기존 방식보다 소요 시간이 줄고 수정 회차가 2회 이하인가. ② 관찰 대상이 Cora 결과물을 수정 후라도 실제 납품·게시에 썼는가. ③ 다음 주에 스스로 다시 열었는가, 그리고 월 이용료로 얼마를 말했는가. 세 가지 중 ②와 ③이 한 사람에게서라도 확인되면 유료 파일럿 제안을 시작할 근거가 있고, 셋 다 확인되지 않으면 기능 추가보다 첫 고객 정의를 다시 검토해야 한다. 표본은 2~4명이므로 시장 전체의 시간 절감으로 표현하지 않는다.

## D. 고객 검증과 사업 검증

### D1. 협력자가 있을 때 필요한 역할

대행사 담당자 1명(브랜드 2개 이상 운영)이나 크리에이터 1명(주 2회 이상 게시)이 60분 관찰 1회와 2주 뒤 30분 재방문에 응하면 된다. 그들에게 요청하는 것은 최근 게시물 1건을 만든 과정을 그대로 보여주는 것, 같은 자료로 Cora에서 1건을 만들어 보는 것, 그리고 F3의 질문에 답하는 것이다. 자료는 공개된 것이나 본인이 허가한 것만 쓰고, 고객사 미공개 자료는 받지 않는다.

관찰에서 적어야 하는 것은 ① 현재 쓰는 도구와 단계 ② 작업·수정에 걸리는 시간 ③ 가장 반복적이고 불편한 일 ④ Cora 결과물을 실제로 쓸 수 있는지(그대로/수정 후/못 씀) ⑤ 다시 쓸 이유와 중단할 이유 ⑥ 비용을 낼 만한 가치가 무엇인지(금액과 조건)다. "좋다"는 평가는 기록하되 판단 근거로 쓰지 않는다.

### D2. 외부 협력자가 없을 때의 대체 과제

동료 학생 2명을 "브랜드 2개를 맡은 담당자"로 설정해 같은 절차를 진행한다. 이 경우 ⑥ 비용 항목은 "본인이 담당자라면"이라는 가정으로 묻고, 결과 표에 "대체 관찰"로 표시한다. 대체 관찰은 사용성 문제를 찾는 데는 유효하지만 유료 가능성 판단에는 쓰지 않는다.

### D3. 고객 모집의 책임 분담

후보 소개와 첫 연락은 교수가 맡고, 학생은 후보 명단 정리·연락 문안 작성·관찰 진행·기록을 맡는다. 학생이 지인을 후보로 올릴 수는 있으나, 모든 외부 발송(이메일·메시지)은 교수 승인 뒤에만 한다.

## E. 측정과 수정

### E1. 핵심 지표 6개

| 지표 | 정의 | 어디에 기록 | 목표는 없고 변화를 본다 |
|---|---|---|---|
| 제작 소요 시간 | 자료 입력 시작부터 PNG ZIP 다운로드까지 분 | 사용실험기록 경과분 | 2·4·8주차 같은 조건 비교 |
| 수정 회차 | AI 초안 대비 사람이 고친 카드 수와 문구 수 | 사용실험기록 수정회차 | 브랜드 메모가 늘수록 줄어드는지 |
| 사실 오류 수 | 원문에 없는 날짜·수치·주장 개수 | 사용실험기록 사실오류수 | 0이 아니면 원문 위치 기록 |
| 결과물 채택 | 그대로 사용/수정 후 사용/미사용 | 사용실험기록 실제납품·미채택이유 | 관찰 대상 기준 |
| 완료율 | 주간 계획 과제 중 완료 개수 | 주간 보고 | 3주 연속 50% 미만이면 과제를 줄인다 |
| 도움 요청 횟수 | 막혀서 교수 또는 AI에게 물은 횟수와 주제 | 주간 보고 | 같은 주제 3회면 문서·화면 개선 대상 |

"AI 품질이 좋다" 대신 관찰할 것은 사실 오류 수, 고친 카드 수, 그리고 관찰 대상이 결과물을 실제로 가져갔는지다. 표본이 10건 안팎이므로 평균만 보고 "시간이 40% 줄었다"고 쓰지 않고, 건별 값과 조건(자료 난이도, 학습 효과)을 함께 적는다.

### E2. 직접 수정할 수 있는 범위와 검토가 필요한 범위

| 처음부터 학생이 직접 | 3주차까지 패치 2건 반영 뒤 확장 | 교수 또는 전문 검토 필요 |
|---|---|---|
| 화면 문구, 안내 문장, 빈 상태 표시, 라벨 | 입력 검증(길이·형식·필수값), 필터·정렬, 목록 화면 추가, 작은 기능(즐겨찾기·문자 정렬) | 로그인·세션·권한, 실제 게시·외부 API, 결제, DB 스키마 변경, 의존성 보안 업데이트, 배포 설정 |

범위 확장 기준은 "패치가 시험과 함께 저장소에 반영됐는가"다. 학생이 만든 시험 결과도 증거 파일을 직접 확인하고, 이해하지 못한 권한·토큰 처리 변경은 제출하지 않는다.

### F7. 코드 수정 파일(패치) 제출 방식

조유경은 GitHub 계정 없이 작업한다. `HYU-BDML/Rita-agent`가 공개 저장소이므로 계정 없이 내려받을 수 있고, GitHub에 올리는 일은 교수 쪽(교수·Claude·Codex)만 한다.

1. 처음 한 번, 조유경 컴퓨터의 일반 폴더(Drive 동기화 폴더 밖)에서 `git clone --branch cora/project-bootstrap https://github.com/HYU-BDML/Rita-agent.git`을 실행한다.
2. 매주 작업 전에 `git pull`로 교수 저장소의 최신 코드를 받는다. 이전 주에 올린 패치가 반영됐는지 `git log -5`로 확인한다.
3. AI와 코드를 고치고 화면에서 확인한 뒤, `Cora` 폴더에서 `git diff > W0_주제.patch`로 패치 파일을 만든다.
4. 패치 파일과 짧은 설명(F4 양식의 "완료 판정 방법" 포함)을 Drive `outputs/조유경_10주/패치/`에 올린다.
5. 교수 쪽 AI가 패치를 적용해 빌드·시험을 실행하고, 통과하면 교수 GitHub의 `cora/project-bootstrap`에 커밋한다. 결과(반영·수정 요청)는 같은 폴더의 `패치_처리기록.md`에 적는다.
6. 반영된 뒤에는 조유경이 `git checkout .`로 자기 사본의 수정을 지우고 `git pull`로 반영본을 받는다.

교수 컴퓨터의 Drive 개발 폴더(`work/rita-agent-source`)는 교수·Claude·Codex가 한 번에 한 도구만 수정하며, 조유경은 그 폴더를 직접 열어 고치지 않는다. 패치에 `.env`, `data/cora`, 생성 미디어, `node_modules`, 키를 넣지 않는다.

## H. 실제 게시 시험 계획

실제 게시는 지금 코드에 연결돼 있지 않다. Blotato 공급자 어댑터는 계약 모의 시험만 했고, Instagram·TikTok·YouTube 공식 API 연결은 없다. 연결 방식은 두 가지다.

| 방식 | 필요한 것 | 장단점 |
|---|---|---|
| Blotato 경유 | Blotato 유료 구독 1개, 연결할 SNS 계정 | 코드 일부가 이미 있어 가장 빨리 시험 가능. 새 구독 비용이 생긴다(금액 확인 필요). |
| 플랫폼 공식 API 직접 연결 | Instagram 비즈니스 계정과 Meta 개발자 앱, YouTube Google Cloud 프로젝트, TikTok 개발자 앱 | 구독 비용은 없다. 플랫폼별 심사 전에는 게시 범위가 제한될 수 있어(예: 심사 전 앱의 공개 범위 제한) 플랫폼마다 확인이 필요하다. |

어느 방식이든 게시 대상은 브랜드 실제 계정이 아니라 시험 전용 계정으로 한다. 플랫폼별 첫 실제 게시는 교수가 화면에서 확인한 뒤 실행하고, 그 뒤 조유경이 C절 6단계를 실제 게시로 반복한다. 실제 게시 시험이 가능해진 주에는 그 주의 코드 과제(1.5시간)를 "실제 게시 시험"으로 바꾼다. 과제 내용은 승인본 1건을 시험 계정에 즉시 게시 1회·예약 게시 1회 올리고, Cora에 기록된 게시 상태·게시물 주소가 실제 게시물과 같은지, 실패 시 중복 게시 없이 "결과 불명"으로 멈추는지 확인하는 것이다.

이 네 가지(D2·D3·D5와 H절 방식 선택) 외의 항목(과제 순서 조정, 코드 과제 범위, 대체 관찰 전환)은 중간 점검 기준에 따라 학생과 AI가 진행하고 주간 보고로 알린다.
