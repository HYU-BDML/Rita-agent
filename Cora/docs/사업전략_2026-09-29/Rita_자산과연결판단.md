# Rita와 신규 콘텐츠 운영 서비스의 연결 판단

작성: 2026-09-29. 조사 범위: 사용자가 지정한 AI Labor Market 폴더의 로컬 기획·회의·인계 문서와 트렌드 레이더/카드뉴스 렌더 코드. 원본은 변경하지 않았다. 비밀키·환경파일·개인 자격증명은 조사하지 않았다. 실서비스에 로그인하거나 생성·발행 요청을 보내지 않았다.

## 판단

신규 대행사 서비스를 Rita의 첫 실전 업무 앱으로 만드는 방향은 맞다. 다만 이번 서비스의 유료 반복 사용을 검증하는 일과 Rita의 다면시장 자체를 검증하는 일은 별개다. 먼저 하나의 업무가 돈을 받고 반복되는지를 입증하고, 그 업무를 처리한 실행·수정·납품·성과 기록을 Rita와 호환되게 남기는 순서가 좋다. 처음부터 범용 에이전트 빌더, 스킬 거래, 포인트, 경연, 정산, SNS 운영 도구를 모두 완성할 이유는 없다.

현재 자료는 '모든 준비가 끝났다'고 판단할 근거가 아니다. 구현 재료가 있고 Rita의 기본 임베드 앱이 배포·시연되었다는 내부 기록은 있지만, 신규 유료 고객의 지불·반복 사용·원가·성과 수집을 입증한 기록은 이번 조사에서 확인하지 못했다. 특히 최근 기록에 API 비용 부담 주체가 달리 쓰여 있고, 프록시·회신·대시보드 설계와 실제 개발 우선순위가 다르다.

## 문서 간 충돌: 새 헌법에서 정리해야 할 부분

1. **API 비용과 최초 체험.** 9/11 전략문서는 오너가 키를 Rita 금고에 넣고 비용을 부담한다고 적었다. 같은 날 개발자 미팅은 학생 공급자 키를 설명한다. 9/15 학생팀 미팅은 마켓 이용자가 자기 API 키를 발급·입력하도록 지시한다. 동일한 운영정책으로 합쳐 쓸 수 없다. 상업 대행사 제품에서는 최초 샘플을 보기 위해 키 발급부터 요구하면 낮은 진입장벽 목표와 충돌한다. 제안은 제한된 무료 샘플 비용을 서비스 원가로 편성하고, 유료 플랜에 사용량을 포함하는 것이다. 고사용량 고객용 BYOK는 이후 선택지로 검토한다. 수업 비용정책을 유료제품의 온보딩에 그대로 옮기지 않는다.

2. **실행·성과 추적.** 9/11 전략문서는 프록시·성과 배지·회신을 강조하지만 실제 개발자 미팅은 SNS 지표 회수를 보류하고 경연·심사를 다음 일로 잡았다. 설계 의지와 구현 완료를 구분해야 한다. 새 서비스는 자체 run_id를 먼저 남기고 Rita 연동은 어댑터로 붙일 수 있다.

3. **모델 로그와 고객 성과.** 기존 전략문서의 '프록시 원장이 재구매율·실제 조회수를 공짜로 준다'는 표현은 수정해야 한다. 모델 호출 로그는 호출량·원가·처리 상태를 알려 준다. 조회수는 게시 ID와 SNS 지표 조회, 재구매는 결제·계약 갱신 기록이 있어야 안다. 서명된 회신 역시 공급자 신원을 확인할 뿐 산출물의 품질이나 사업 성과를 자동 입증하지 않는다.

4. **데이터 소유.** 기존 문서의 '성과 기록은 Rita 소유'는 설계 희망을 법적·계약적 확정으로 취급하면 안 된다. 고객 원자료·브랜드 규칙·수정 피드백·계정 지표는 사용 목적과 접근 권한을 구분해야 한다. 실행 메타데이터 보관, 익명 집계 활용, 공개 포트폴리오, 다른 고객 추천에 활용하는 행위는 별도 정책으로 정의해야 한다.

5. **수업과 시장.** 학생의 수강 과제 제출·강제 사용·코드 공개는 외부 고객의 지불 의사나 자발적 잔존을 입증하지 않는다. 수업은 품질 문제 발견과 사용성 시험에 유용하다. 상업 검증 수치에는 수업 표본을 섞지 않는다.

## 실제로 재사용할 수 있는 구현 자산

### 트렌드 레이더

로컬 구현은 FastAPI + SQLite이며 탐색·채널 대비 이상치·감시/추세·해외 소재·한외 비교가 존재한다. `backend/app/db.py`에는 영상/채널/기준값/지표 스냅샷/감시 목록/아이디어/일별 쿼터 테이블이 있다. `watch.py`는 채널 검증, 일별 스냅샷, 미완료·실패 표시 등 운영상 발견한 문제를 처리한다. 이는 재사용할 가치가 있는 경험이다.

그러나 현행 인증은 API 키 허용목록이고, `watched_channels`는 채널 ID가 전역 기본키, `ideas`에는 테넌트 식별자가 없다. 감시 목록과 아이디어가 고객별로 분리되는 SaaS 구조로 확인되지 않는다. `list_watched()`는 전체 목록을 읽고 `remove_watch()`는 채널 ID 하나로 삭제한다. 원래 학생·도구 공유 환경의 구조를 여러 고객사 운영 서비스로 그대로 노출하면 안 된다.

공개 영상·공개 트렌드 수집 캐시는 공용으로 둘 수 있다. 하지만 '누가 무엇을 저장·감시·기획했는가', 비공개 브랜드 정보, 고객 계정 지표는 고객 범위를 붙인 새 저장소가 필요하다. 점수 공식과 영상 분류는 이전 조사에서 문서/코드 차이까지 확인했으므로 공식 설명을 다시 고정해야 한다.

### 카드뉴스 렌더

`src/server.py`는 덱 JSON→PNG, 상태 확인, 디자인 측정·저장 등을 처리한다. 손질판·부분 수정·평가·디자인 자료가 함께 존재한다. Dify가 구조화된 콘텐츠를 만들고 렌더러가 이미지를 굽는 경계는 유지할 가치가 있다. 생성 모델을 바꾸더라도 편집·렌더를 재사용할 수 있기 때문이다.

다만 README는 겉모습 추출 제외라고 쓰지만 코드에는 `/measure`·`/styles` 분기가 있다. 9/29 인계는 옛 렌더 주소가 남아 있는 배포본과 미통합 상태를 기록한다. 전체 유형의 최신 품질, 고객별 접근통제, 상용 운영 용량이 확인된 것은 아니다. 새 서비스에서 이 서버를 내부 렌더 워커로 재사용하고 사용자 자산 접근은 서비스가 통제하는 방식을 제안한다.

### Dify 및 샘플 디자인

소재발굴과 카드뉴스의 입출력·유형별 규칙·평가 사례는 자산이다. 워크플로 전체를 사용자 UI로 노출할 필요는 없다. 구조화된 입력을 받아 주제·근거·카드 문구·레이아웃을 반환하는 함수 경계로 감싸면 독립 서비스와 Rita가 모두 호출할 수 있다. 기존 브랜드를 따라 만든 디자인은 품질 학습자료와 상업 배포용 템플릿을 구분해 검토한다.

## Rita와 공용화할 것, 제품 안에 둘 것

| 공용 경계 | 최소 공통 규격 | 이번 제품 안에서 별도 유지 |
|---|---|---|
| 사용자·조직 식별 | 외부 사용자와 로컬 사용자 매핑, tenant_id, membership, role | 대행사별 브랜드/담당자 화면·고객 승인 포털 |
| 작업 실행 | run_id, parent_run_id, agent_id/version, 입력 스키마 버전, 상태, 시간, 오류 | 소재→기획→초안→수정→승인이라는 콘텐츠 업무 상태 |
| 결과물 | artifact_id, 버전, 종류, 저장 위치, checksum, 권한, 보존정책 | 카드 편집기, 템플릿, 폰트·이미지·브랜드 표현 규칙 |
| 원가·사용량 | 모델/렌더 등 작업별 실제 비용과 수량, 청구 계정, 상한 | 패키지 가격, 고객사 수, 납품 묶음 등 대행사 가격 정책 |

| 모듈 등록 | 목적·입력·출력·예시·권한·요금·버전 | 고객의 실제 자료나 비공개 브랜드 규칙 |
| 외부 연결 | 제한된 권한으로 연결 서비스 호출 | Instagram 계정 자격증명과 발행 허용 범위, 발행 안전장치 |

공용화는 처음부터 별도 마이크로서비스를 여럿 운영한다는 뜻이 아니다. 하나의 코드베이스에서도 모듈·스키마·버전을 구분하고 나중에 Rita 어댑터를 붙일 수 있다. 사업 검증 전에 범용 런타임을 새로 만드는 일은 피한다.

## 연결 흐름 제안

1. 독립 서비스 방문자는 Rita 계정 없이도 제한된 샘플을 확인한다. 실제 저장·협업 시 서비스 계정을 만든다.
2. Rita에서 실행하면 짧은 수명의 교환 코드를 서버에서 검증해 로컬 조직·사용자·권한과 연결한다. 조직이 같다는 추정만으로 계정을 자동 합치지 않는다.
3. `run_id`를 발급하고 작업 입력/권한/모듈 버전을 기록한다. 생성은 작업 큐에서 처리하며 실패·취소·비용상한을 표시한다.
4. 결과물과 수정 버전이 저장되고, 고객 승인은 승인자가 본 정확한 버전에 붙는다.
5. SNS 발행은 별도 권한과 승인 상태를 확인한 전용 서비스만 실행한다. 콘텐츠 생성 모듈이나 외부 공급자 앱에 계정 토큰을 넘기지 않는다.
6. 게시 ID를 결과물 버전과 연결한 뒤 시점별 지표를 수집한다. 실제 API 관측, 고객 입력, 공급자 보고를 다른 증거 수준으로 표시한다.
7. Rita에는 허용된 실행/결과 요약 이벤트만 회신한다. 고객 자료·SNS 토큰·전체 작업 대화가 기본적으로 Rita 마켓에 공개되지 않는다.

모듈 예: `discover_material`, `draft_carousel`, `render_carousel`, `review_brand_rules`, `analyze_published_content`. 실제 Instagram 발행은 외부 영향이 있는 작업이므로 일반 콘텐츠 모듈과 권한을 분리한다.

최소 이벤트 필드 제안:

```json
{
  "event_id": "uuid",
  "schema_version": "1",
  "tenant_id": "agency_or_business_id",
  "brand_id": "brand_id",
  "run_id": "uuid",
  "parent_run_id": null,
  "agent_id": "draft_carousel",
  "agent_version": "1.0.0",
  "artifact_id": "uuid",
  "artifact_version": 3,
  "event_type": "artifact.approved",
  "occurred_at": "ISO-8601",
  "actor_type": "client_reviewer",
  "evidence_source": "first_party_workflow",
  "consent_scope": "private_client_workspace"
}
```

위 스키마는 제안이며 Rita의 구현된 API가 아니다. 승인 이벤트를 받았다고 발행까지 허용된 것으로 간주하지 않는다. 요청 반복 방지 키, 이벤트 중복 처리, 콜백 서명 검증, 재시도와 권한 철회도 구현할 때 함께 정의해야 한다.

| 고객 업무에 쓰였나 | 승인/납품/실제 게시 | 추가 매출 |
| 더 편해졌나 | 기존 방식 대비 작업 시간·수정 횟수·채택률 | 조회수 상승 |
| 더 효과적이었나 | 게시 시점·포맷·유료노출·기존 팔로워 등 맥락과 지표 | 단순 조회수 차이만으로 에이전트의 인과적 효과 |
| 실제 사업인가 | 비지인 외부 고객 결제·반복 결제·기여이익 | 수업 사용량·무료 이용 후기 |
| Rita 시장이 작동하나 | 제3자 공급자 선택·구매·반복 거래와 성공적 납품 | 자사 앱 하나가 잘 팔리는 것 |

조회수가 높은 브랜드만 특정 에이전트를 사용하면 순위가 왜곡된다. 수정 인력과 광고비가 다른 결과를 단순 랭킹으로 묶지 않는다. 처음에는 '검증된 성장' 배지보다 결과물이 실제 승인·게시되었는지, 같은 고객이 다시 쓰고 돈을 냈는지 정확히 보여주는 편이 낫다.

## 범위 팽창을 막을 판단

- 첫 대행사 서비스의 고객 문제를 해결하는 기능과 Rita의 먼 미래에만 필요한 기능을 구분한다. 이번 제품 고객에게 직접 효용이 없으면 공통 데이터 규격만 남기고 기능 구현은 미룬다.
- 크리에이터 고객이 유료 반복 사용에서 더 좋게 나오면 같은 엔진에 1인 작업실·자기 승인·계정 운영 화면을 붙일 수 있다. 다중 브랜드/협업은 기본 기능의 강제가 아니라 필요할 때 켜는 구조로 한다.
- 'Rita로 쪼갤 수 있음'은 기술 요건, '여러 고객이 실제 그 조각을 원함'은 시장 요건이다. 모듈 거래는 후자가 확인될 때 연다.
- 대행사가 자신의 고객사를 서비스에 초대할 때, 브랜드 계약 해지·담당자 퇴사·권한 철회·자산 반환을 처리할 수 있어야 한다. 대행사 관리자 권한과 고객사 관리자 권한을 동일하게 취급하지 않는다.
- 원본 API 키와 SNS OAuth 토큰은 다른 목적의 비밀이다. 어느 모듈이 어떤 브랜드 계정으로 무엇을 할 수 있는지 서비스가 결정하고, 클라이언트가 보낸 brand_id만 믿지 않는다.
- 외부 앱 임베드는 로그인·화면 표시일 뿐, 작업 순서 연결·권한 공유·성과 검증을 자동 제공하지 않는다.

## 추가로 전달된 실제 인력·예산 제약 반영

부모 작업에서 전달된 제약은 학생 2–3명, 각 주 4–5시간(합계 주 8–15시간), 경영 전공이지만 프로그래밍 가능, 디자인 프리랜서 동료 협력 가능, 대행사·크리에이터 고객 접근은 아직 미확보다. 8주면 명목 64–120시간이며 수업·조율·검증·장애 대응을 빼면 실제 개발 시간은 더 적다. 이 조건에서 멀티테넌트 SNS 생성·편집·고객 승인·OAuth 발행·지표 수집 SaaS 전체를 약속하면 안 된다.

첫 검증은 기존 Dify/렌더를 운영자가 사용해 '고객사 1곳의 다음 주 콘텐츠 납품팩'을 만드는 방식이 적절하다. 고객에게는 브랜드 자료와 소재 요구를 받고 카드뉴스 초안·문구·수정 가능한 소스·게시 계획을 제공한다. 발행은 고객의 기존 방식으로 하고, 실제 게시 링크·가능한 성과 자료를 허락받아 회수한다. 이 단계에서 실제 계정 연결·자동 발행·범용 Rita 프록시를 만들 필요는 없다. 고객이 돈을 내고 두 번째 납품을 요구하는지부터 본다.

필수 작업은 네 가지다. ①옛 주소가 남은 워크플로를 원본 보존 후 복사본에서 연결·유형별 최소 검증, ②상업 사용 가능한 템플릿 소수의 품질을 디자이너와 고정, ③고객별 작업 폴더/메타데이터를 분리하고 결과·수정·승인 기록 남기기, ④비지인 잠재고객 접촉과 실제 납품 실험. Rita 통합은 `run_id`, 모듈 버전, 결과물 버전, 작업 시간, 직접비, 고객 승인/반려 정도를 CSV/DB에 기록하는 것으로 시작해도 충분하다.

월 몇십만 원은 제한된 텍스트·정적 카드뉴스 파일럿의 비용 상한으로 검토할 수 있지만, API 종류·생성 횟수·영상 재시도·저장 기간·무료 고객 수가 정해지기 전에는 충분하다고 확정할 수 없다. 현행 유료 Render와 모델 비용도 이번 조사에서는 과금 내역을 열람하지 않았다. 먼저 한 납품팩의 실제 원가와 운영자 소요 시간을 측정하고, 그 비용 상한 안에서 체험 고객 수를 정해야 한다. 비용에 학생·본인·디자이너 시간이 0원이라고 가정하면 사업성 계산이 왜곡된다.

가장 먼저 필요한 인력은 범용 플랫폼 개발자가 아니라 고객의 실제 수정 이유를 기록할 운영자와 출력 품질을 잡을 디자이너다. 학생 개발시간은 이 두 작업에서 반복되는 병목 하나를 없애는 데 배분하는 것이 Rita 자산도 남기면서 실패 비용을 줄인다.
