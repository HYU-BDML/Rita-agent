콘텐츠 플랫폼: 벤치마크와 새 제품 설계

2026-09-29 조사. 국내 8개·해외 24개 대안, 기존 Mirr 분석 및 Claude 코드·인계 문서 검토.

추천: 대행사의 고객별 제작·승인 업무를 중심에 놓고, 소재 수집과 편집을 연결한다. 제작 엔진은 기존 트렌드 레이더·카드뉴스 서버를 재사용하되, 별도의 새 사이트·저장소·데이터 저장소에서 개발한다. 기존 서비스는 유지한다.

아래 순위는 공식 공개 자료를 토대로 판단한 ‘우리 제품에 가져올 가치와 조사·적용 우선순위’다. 실제 고객의 구매 순위나 한국어 생성 품질 실험 결과가 아니다. Mirr보다 모든 면에서 우수하다고 확인한 서비스는 없다. 기능별로 Mirr 분석에서 확인하지 못했거나 더 깊게 설계할 수 있는 구조를 찾았다. 실제 로그인 후 생성·편집·발행을 32곳 모두 실행한 것은 아니다. 소개·도움말 근거를 구분하고, 확인하지 못한 성능은 한계에 적었다.

판단 순서: ① 고객 업무에서 자주 발생하는 병목 ② 소재→결과→승인의 연결 ③ 수정·재사용 편의 ④ 기존 자산과의 연결 가능성 ⑤ 독자 데이터·모델에 대한 의존. 숫자 점수를 임의로 붙이지 않았다. 후순위 서비스도 특정 기능에서는 우선 참고 대상이다. 요금은 구매 시점과 규모에 따라 달라 이번 순위에 확정 비용으로 넣지 않았다.

2. 고객별로 순위가 달라진다

고객 가설우선 참고 순서결정 이유
소규모 광고·콘텐츠 대행사 — 1차 추천Planable → ContentStudio → Canva → Metricool → Predis.ai제작량보다 수정·승인·버전 혼선이 반복되는 문제를 먼저 해결한다. 퍼포먼스 광고 전문 회사라면 Predis.ai·AdCreative.ai의 변형과 실험 관리 비중을 높인다.
개인·소규모 콘텐츠 크리에이터 — 2차 추천Descript → OpusClip → Viewstats → Vrew → Buffer소재 선정, 원본 재가공, 자막·말투 수정, 여러 채널 발행을 짧게 연결한다.
브랜드의 소규모 사내 마케팅팀 — 3차 가설SocialBee → Jasper → Canva → Feedly → Metricool제품 사실·브랜드 기준을 유지하면서 주간 운영을 끝낼 수 있어야 한다.

이는 고객 인터뷰 전 제품 가설이다. 세 종류를 동시에 완성하려 하지 않고, 공통 제작 기반 위에 시작 화면·기본값·승인 방식만 다르게 둔다. 모든 광고회사에 같은 업무를 가정하지 않는다. 우선 SNS 콘텐츠 대행을 중심으로 하고 광고비 집행·입찰 최적화는 뒤로 둔다.

3. 첫 고객이 실제로 하는 일

광고·콘텐츠 대행사

담당자가 고객 브랜드를 선택한다 → 이번 달 목표·제품 사실·금지 표현·발행 수량·승인자를 확인한다 → 소재 후보를 근거와 함께 세 개로 좁힌다 → 기획안을 내부 승인한다 → 카드뉴스와 채널별 문구를 만든다 → 디자이너가 고정 로고 외의 요소를 수정한다 → 고객에게 해당 버전만 공유한다 → 반려 의견이 붙은 카드만 수정한다 → 최종 승인된 버전을 예약한다 → 월말에 게시물과 목표별 성과를 보고한다.

홈에는 고객별 ‘내가 처리할 수정’, ‘고객 승인 대기’, ‘오늘 발행’, ‘실패한 작업’을 우선 배치한다. 프롬프트 입력창을 홈 전체로 쓰지 않는다. 고객 화면에는 승인할 결과·변경점·일정만 보여 주고 내부 메모와 다른 고객의 자료는 숨긴다. 기획 승인과 최종 발행 승인은 다르게 기록한다.

콘텐츠 크리에이터

본인의 영상 또는 링크·아이디어를 넣는다 → 채널 평소 대비 잘된 사례와 원본의 쓸 만한 장면을 본다 → 독자에게 줄 한 가지 메시지와 시작 문구를 선택한다 → 쇼츠·카드뉴스·게시글 묶음을 만든다 → 글에서 군더더기를 지우고 자막을 고친다 → 채널별 미리보기를 확인한다 → 발행하거나 파일을 내보낸다 → 다음 소재에 적용할 관찰을 저장한다.

홈의 큰 버튼은 ‘원본으로 여러 콘텐츠 만들기’다. 전문 타임라인은 필요할 때 열고, 기본 편집은 문장·카드·장면 단위로 한다. 본인 최종 확인을 기본 승인으로 쓰며 고객 결재 단계를 강제하지 않는다.

브랜드 마케팅팀

웹사이트와 제품 자료를 등록한다 → 자동 추출한 제품 사실을 검수한다 → 월간 목표와 고객군을 고른다 → 주간 콘텐츠 계획을 받는다 → 신제품·혜택·기간 정보를 적용한다 → 사실과 브랜드 기준을 검수한다 → 상급자 확인 후 발행한다 → 반응·유입·전환을 구분해 다음 주 계획을 바꾼다.

홈에는 ‘이번 주 계획’과 ‘확인이 필요한 제품 정보’를 둔다. 제품 가격·혜택·마감일에는 유효기간을 붙인다. 게시글이 잘됐다는 이유로 오래된 할인 정보를 재발행하지 않는다.

4. Mirr보다 편하게 만들 구체적인 설계

이 절은 외부 서비스의 내부 구현을 알아낸 것이 아니라, 조사에서 얻은 원리를 조합한 자체 설계다.

5. 화면 구조

공통 왼쪽 메뉴: 오늘 할 일 / 소재 찾기 / 제작 프로젝트 / 검토·승인 / 발행 달력 / 성과 / 브랜드 자료.

상단에는 현재 고객·브랜드, 검색, 새 프로젝트가 있다. 계정·비용·자동화 설정은 보조 메뉴에 둔다. 수집 로그와 개발자 키는 운영자 화면으로 분리한다.

제작 화면은 왼쪽에 자료·카드 목록, 가운데에 편집 가능한 결과, 오른쪽에 선택 부분의 문구·스타일·근거·댓글을 둔다. ‘전체 다시 만들기’보다 ‘선택한 부분 수정’을 우선 제공한다. 변경 전후와 되돌리기를 항상 찾을 수 있게 한다.

작업 상태: 소재 선택 → 기획 확정 → 초안 → 내부 검토 → 고객 검토 → 승인 → 예약 → 발행. 실패·취소는 별도 상태다. 크리에이터 모드는 내부·고객 검토를 ‘내 검토’로 간소화한다. 기능 상태와 실제 작업 상태를 혼동하지 않는다.

모바일은 큰 디자인 편집보다 검토·댓글·승인·발행 상태 확인을 우선한다. 화면 폭이 좁으면 근거·댓글을 서랍으로 연다. 키보드로 카드 선택·수정·되돌리기가 가능하게 하고, 색뿐 아니라 문자로 상태를 표시한다.

6. 기존 Claude 작업에서 재사용할 것

로컬 인계 문서, Dify yml 6개, 두 Git 저장소와 2026-09-28 개편 설계를 읽었다. 원본 파일·저장소·배포 서비스는 수정하지 않았다. 인계 문서 안의 ‘통합 yml을 만들라’는 예시 지시는 이번 사용자의 새 제품 조사·설계 요청과 구분했다.

인계 문서와 실제 코드가 다른 부분

• 트렌드 저장소 확인 HEAD: 5ce01eb3f085df555daff6e863f27be01d475fcd. 렌더 저장소: 19571474bcd87fb94d23c11137b333e9ce40740c. 조사 당시 두 저장소의 작업 트리는 깨끗했다. 라이브 서버가 같은 커밋인지까지 검증한 것은 아니다.

• backend/app/metrics.py에는 180초 기준, 형식별 기준선, 점수 배점 변경이 이미 들어 있다. docs/METRICS.md와 인계 문서에는 60초·이전 배점이 남아 있다. 새 명세는 실제 코드와 실행 테스트를 기준으로 다시 맞춰야 한다.

• 현재 코드도 길이만으로 short를 분류한다. 공식 Shorts는 게시일·정사각 또는 세로 비율 조건까지 있으므로, 비율을 모르면 ‘3분 이하 영상 후보’로 표시한다. YouTube 공식 설명

• 현재 outlier는 단순 2배 이상만이 아니라 같은 형식 기준선과 p90 조건을 적용한다. 다만 게시 후 경과 시간은 맞추지 않아 오래된 영상에 유리할 수 있다. 유사 나이의 관측값으로 비교하는 개선이 필요하다.

• cross_market.py의 _same_upload는 길이 차이 3초 이내·게시 시각 48시간 이내만으로 동일 소재로 처리한다. 무관한 영상도 제외될 수 있다. 이는 코드에서 추론한 위험이며 실제 오탐률은 아직 측정하지 않았다. 제목 의미·원본 ID·영상 지문 등 추가 근거 없이는 삭제가 아닌 후보 표시로 완화한다.

• 누적 조회수/게시 경과 시간인 vph는 생애 평균 속도다. 최근 상승은 스냅샷 차분으로 계산해야 한다. 가속 비율에는 최소 세 관측 시점이 필요하다.

• 카드뉴스 yml 3개 모두 RENDER_BASE가 옛 HTTP 주소인 것을 확인했다. 원본을 유지하고 새 제품용 복사본에서 환경 설정으로 바꿔야 한다. 주소 변경만으로 전체 작업 정상 동작을 보장하지 않는다.

• 렌더 README에는 겉모습 뜨기가 배포 제외라고 되어 있지만 현재 server.py는 /measure·/styles 경로를 처리하고 Google Vision 환경 변수도 선언한다. 문서가 오래된 가능성이 높지만 실제 OCR 성공 여부는 미검증이다.

• 모델명은 배포 yml에 적힌 식별자일 뿐 현재 공급자에서 호출 가능하다는 증거가 아니다. 새 제품에서는 모델 공급자를 교체 가능한 서버 설정으로 둔다.

• 일괄 Dify의 for_next.data는 JSON 문자열이다. 고른_주제, 판정, 근거_링크, 따라만들_본보기를 파싱해야 한다. 제목·링크만으로 사실 원고를 생성하면 자료를 읽지 않고 내용을 추측하는 문제가 생긴다.

7. 새 사이트의 연결 구조

새 웹앱 → 프로젝트 API·계정 권한 → 작업 큐 → (자료 수집 어댑터 / 원고 작성 / 이미지·영상 공급자 / 렌더 작업자) → 버전 저장 → 검토·승인 → 발행 어댑터 → 성과 수집.

Dify는 교체 가능한 원고·자료 처리 엔진으로 감싼다. 고객 계정, 프로젝트 상태, 버전, 승인, 비용을 Dify 내부 대화 상태에만 저장하지 않는다. 렌더 서버의 기존 HTML·스타일 방식은 출발점으로 활용하되 편집 가능한 덱 JSON을 원본으로 둔다. PNG만 저장하면 나중에 글자 하나를 고칠 때 원본을 잃는다.

공통 객체: Workspace / BrandProfile / SourceItem / Evidence / Brief / ContentProject / ArtifactVersion / Approval / PublishJob / MetricSnapshot. 모든 고객 자료에는 workspace_id를, 모든 생성 결과에는 입력 자료·프롬프트·모델·템플릿 버전을 기록한다. 다른 계정에서 같은 공개 기사를 수집하더라도 고객 메모·프로젝트는 공유하지 않는다.

SourceItem은 URL·제목·수집 시각·원문 확보 여부·권리 상태·플랫폼 지표를 가진다. Evidence는 주장·근거 위치·자료 ID·검수자를 가진다. ArtifactVersion은 편집 가능한 카드/장면·자산 참조·이전 버전 ID를 가진다. Approval은 사용자와 정확한 artifact_version_id에 묶인다. 비용은 생성 요청별 예상·실제·환불·재시도를 별도로 남긴다.

새 Git 저장소에서 시작한다. 기존 두 저장소의 검증된 코드만 출처 커밋을 기록해 복사·어댑터화한다. .env, API 키, 학생 데이터와 기존 결과물은 가져오지 않는다. 새 배포·DB·파일 저장소·테스트 브랜드를 사용한다. GitHub는 코드·변경 이력·테스트·배포를 연결하는 곳이며, 실제 AI·SNS 연결 키와 작업 결과 DB를 대신하지 않는다. 이번에는 원격 저장소를 만들거나 배포하지 않았다.

8. 구현 순서와 통과 기준

단계만들 결과출시 전 통과 기준
1. 핵심 한 흐름소재 선택→근거 확인→6장 카드뉴스→부분 수정→승인→PNG 묶음자료 없이 사실 생성 금지, 한글 넘침 검사, 수정·되돌리기, 재접속 후 동일 결과
2. 대행사 업무고객 공간·내부/외부 검토·버전 승인·템플릿고객 간 접근 차단, 승인 뒤 수정 시 재검토, 반려 의견과 수정본 연결
3. 발행 운영한 SNS부터 예약·실패 재시도·예산 제어실제 OAuth·검수 요건 충족, 중복 발행 방지, 토큰 만료 안내
4. 크리에이터 확장긴 원본→장면 후보→쇼츠→자막 수정타임코드 정합, 원본 연결, 자막·음성 품질, 렌더 실패 복구
5. 성과 개선동일 목표의 버전 비교·템플릿 추천플랫폼·측정창·유료/자연 유입 구분, 충분한 표본 전 효과 확정 금지

실제 고객 검증은 같은 자료로 기존 방식과 새 방식의 작업을 비교한다. 대행사 5명·크리에이터 5명·브랜드팀 3명은 모집 제안이며 실행한 인터뷰가 아니다. 첫 완성본까지 걸린 시간, 수정 횟수, 고객 승인까지 소요 시간, 도구 이동 횟수, 최종 사용 가능한 결과 비율, 채택된 결과물당 비용을 기록한다. 목표값은 파일럿 기준치를 얻은 뒤 정한다. AI 생성량과 조회수만으로 편의성을 판정하지 않는다.

9. 우리가 축적해야 할 노하우

처음부터 자체 AI 모델이 필요한 것은 아니다. 먼저 좋은 결과가 나오는 브랜드 사실·템플릿·편집 규칙·검증 사례를 축적한다. 그다음 고객이 무엇을 수정하고 왜 반려했는지, 어떤 결과를 채택했는지를 구조화한다. 성과 데이터가 쌓이면 플랫폼·고객·노출 조건을 맞춘 추천을 실험한다.

직접 재현 가능한 부분외부 연동이 현실적인 부분시간이 필요한 부분
작업 흐름, 기획 양식, 버전 승인, 편집 UI, 템플릿 규칙, 작업 큐음성·영상 생성, SNS 발행, 일부 자료 수집·분석 API장기 트렌드 관측, 한국어 디자인 검증집, 수정 이유 데이터, 성과 추천의 검증

‘모델이 자동으로 학습한다’는 설명 대신 저장된 브랜드 규칙·검수 사례를 다음 생성에 어떻게 사용했는지 보여 준다. 광고 성과 예측·대규모 트렌드 데이터·정밀 영상 추적은 화면과 프롬프트만으로 동일 품질을 보장할 수 없다. 예측 점수보다 수정 시간을 줄이고 근거와 버전을 잃지 않는 제품이 첫 차별점이다.

10. 이번 결과의 범위

32개 공식 서비스·관련 도움말을 조사한 벤치마크, 고객별 작업 흐름, 16개 구현·검증 항목, 실제 로컬 자산 점검, 새 사이트의 클릭 가능한 화면 초안을 제공한다. 화면 초안은 가상 자료로 동작하는 로컬 시뮬레이션이며 AI 생성·서버 저장·SNS 발행은 연결하지 않았다. 기존 Mirr 보고서는 그대로 보존했다. 홈페이지 홍보의 속도·매출·사용자 수·예측 정확도는 독립 검증된 수치로 채택하지 않았다.

11. 첫 고객에 대한 판단과 이유

첫 고객 추천은 2~10명 규모로 여러 브랜드의 SNS 콘텐츠를 월 단위로 납품하는 대행사다. 인원 범위는 시장 조사로 확정한 통계가 아니라 모집 범위를 좁히기 위한 가설이다. 고객이 3~15개인 팀을 우선 인터뷰해 반복 업무의 양과 복잡도를 확인한다. 광고비 집행·입찰·매체 구매를 주로 하는 회사는 첫 고객에서 제외한다.

왜 이 고객부터인가

1. 이미 가진 기술과 해결할 일이 맞는다. 트렌드 레이더, 원고 생성, 카드뉴스 렌더는 주기적으로 SNS 콘텐츠를 납품하는 과정의 앞부분이다. 전문 영상 도구를 처음부터 완성하지 않아도 소재 선정→카드뉴스→수정→승인→납품을 끝낼 수 있다.

2. 한 번 만든 기준을 반복해서 쓸 이유가 강하다. 고객마다 말투·금지 표현·로고·선호 디자인이 다르며 같은 고객은 다음 달에도 돌아온다. 이 기준과 수정 이유를 저장하면 다음 작업이 편해질 수 있다. 이것이 프롬프트 입력창만 제공하는 도구와 다른 가치다.

3. 생성과 별개인 문제가 있다. 고객에게 잘못된 버전을 보내거나 승인된 문구가 나중에 바뀌는 문제는 더 좋은 이미지 모델만으로 해결되지 않는다. Planable의 단계별 승인과 ContentStudio의 고객 공간은 이 업무를 다루는 확인 가능한 제품 사례다. 이것이 해당 문제가 모든 한국 대행사에서 가장 크다는 증거는 아니므로 인터뷰로 우선순위를 검증한다.

4. 편의의 효과를 측정하기 쉽다. 게시물 하나의 작업 시간, 수정 왕복 횟수, 승인 대기 시간, 납품 오류, 최종 채택률을 비교할 수 있다. 알고리즘에 영향을 받는 조회수만으로 제품 가치를 설명할 필요가 없다.

5. 한 팀 안에서 반복 검증이 가능하다. 여러 고객 브랜드를 다루므로 한 사용자에게서도 서로 다른 템플릿·주제·승인 요구를 관찰할 수 있다. 반면 한 고객의 취향을 모든 고객에게 적용하는 과적합을 피하려고 브랜드별 데이터를 분리해야 한다.

6. 지불 이유를 설명할 수 있는 가설이다. 담당자의 반복 작업과 관리 가능한 고객 수에 영향을 주면 업무 도구 예산으로 검토될 여지가 있다. 실제 매출·마진 개선이나 구매 의사는 아직 확인하지 않았다. 생성 횟수보다 채택된 납품물당 총비용과 줄어든 시간을 함께 보여 주는 것이 맞다.

왜 크리에이터와 브랜드팀은 다음인가

기준SNS 콘텐츠 대행사개인·소규모 크리에이터브랜드 사내팀
현재 자산과의 적합성카드뉴스·소재 수집을 바로 연결 가능영상 중심이면 추가 개발이 큼카드뉴스·제품 소개는 적합
반복되는 기준여러 고객의 고정 브랜드 기준개인 스타일이 강하고 형식 편차 큼제품 사실·브랜드 기준이 강함
먼저 줄일 비용수정·승인·납품 관리편집·아이디어 선정기획·내부 검토·반복 제작
초기 제품 부담권한·고객 분리·버전 승인 필요영상 편집 품질과 사용 편의 경쟁회사마다 승인·자료·보안 요구가 다를 수 있음
구매 가설팀 업무 개선으로 검토 가능개인 예산과 성장 기대에 좌우될 수 있음명확한 담당자가 있으면 좋은 초기 고객 가능
검증 방식같은 고객의 전후 납품 작업 비교같은 원본의 편집·채택률 비교같은 캠페인의 제작·승인 시간 비교

브랜드팀이 항상 판매하기 어렵거나 크리에이터가 돈을 내지 않는다고 단정하지 않는다. 특히 이미 관계가 있는 브랜드 담당자가 실제 자료와 피드백을 빠르게 제공한다면, 그 팀이 익명의 대행사보다 좋은 첫 시험 고객이다. 시장 크기 추정보다 반복적으로 관찰할 수 있는 유료 문제를 먼저 확인한다.

이 선택의 약점과 대응

• 대행사는 초보자가 아니다. AI 초안이 평범하면 그대로 쓰지 않는다. 근거 자료·브랜드 기준·부분 편집과 되돌리기를 핵심으로 두고, 최종 채택 가능한 결과 비율을 측정한다.

• 고객별 맞춤 요청이 끝없이 늘어날 수 있다. 첫 범위를 카드뉴스와 채널별 문구, 내부·고객 2단계 검토, PNG 납품으로 고정한다. 복잡한 계약·정산·CRM은 넣지 않는다.

• 승인 화면은 이미 전문 경쟁사가 있다. 승인만으로 경쟁하지 않고, 국내외 소재 근거→한국어 카드뉴스→고객 수정 이력의 연결을 하나의 프로젝트에 묶는다.

• 권한·버전·저장 신뢰성이 초기에 필요하다. 예쁜 데모만으로 영업을 시작하지 않고 다른 고객 정보 노출 방지와 승인 버전 고정을 먼저 검증한다.

무엇이 확인되면 방향을 바꿀까

대행사 5곳의 실제 최근 납품을 관찰했는데 소재 선정·수정·승인보다 촬영·영업·매체 집행이 큰 병목이면, 이 고객 정의를 더 좁히거나 브랜드팀으로 바꾼다. 생성 결과를 대부분 다시 만들고 기존 도구보다 시간이 더 걸리면 자동화 기능을 늘리지 않고 템플릿·편집 품질부터 개선한다. 크리에이터들이 현재 자산으로 만든 카드뉴스·짧은 정보 콘텐츠를 반복 사용하며 먼저 결제한다면, 그 고객군을 우선할 근거가 된다.

첫 제품의 약속: 고객 브랜드에 맞는 소재를 근거와 함께 고르고, 수정 가능한 한국어 카드뉴스와 게시글을 만들어, 승인된 버전으로 납품한다. 이 약속을 검증한 뒤 영상·자동 발행·성과 추천을 확장한다.

비교 근거는 각 서비스의 공식 자료 링크에서 확인할 수 있다. 기존 Mirr 보고서와 기존 운영 서비스는 그대로 유지했다.
