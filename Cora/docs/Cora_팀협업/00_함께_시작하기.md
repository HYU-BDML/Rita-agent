| 사람 | 주 역할 | 맡기면 좋은 일 | 결정/완료 권한 |
|---|---|---|---|
| 임보람 교수 | 제품 책임자 | 고객/가치/범위 결정, 실제 고객 관찰, 우선순위와 예산 | 출시·실제 첫 게시·비용/권한 승인 |
| 유경 | 사용자/콘텐츠 품질 검수 | 실제 흐름, 브랜드 적합성, 수정량/시간, 재현 가능한 문제, 작은 패치 | 관찰/패치 제출; 직접 운영 DB/배포 책임 없음 |

이는 시작 배정 제안이다. 개발자가 더 나은 구조/우선순위를 제안하면 이유와 이전/검증 계획을 보고 바꿀 수 있다. 기존 AI 계획을 정답으로 강요하지 않는다. 교수/학생/AI90%+ 구현은 목표이며 개발자의 실제 필요 작업량은 검수 후 결정한다.

## 4. 서로의 작업을 덮지 않는 방식

1. 작업 시작 전에 실행 원장의 항목ID 또는 학생 문제ID를 정한다. GitHub Issue를 쓰면 같은ID를 본문에 넣고 링크로 연결한다. 동일 상황을 새 CSV마다 다른 문제로 만들지 않는다.
2. 담당자·현재 기준 commit·변경할 파일·완료 기준·예상 검수/부작용을 작업 메모에 적는다. 같은 파일이면 통합 담당자가 순서를 정하거나 각 브랜치에서 작업하고 PR로 충돌을 해결한다.
3. 개발자는 cora/dev-작업명, AI는 별도 checkout의 cora/ai-작업명 등 task branch를 사용한다. 교수 Drive checkout은 현재 브랜치를 유지한다. 학생은 GitHub 계정 없이 지금처럼 patch로 제출해도 된다.
4. PR/patch → 다른 사람이 재현/관련 시험 → 통합 브랜치 반영 → 통합 회귀 → 원장/공동 상태·outputs 갱신. PR을 만들었다는 사실과 실제 반영/완료는 별개다.
5. 본인 AI와 다른 AI가 **같은 checkout**을 동시에 수정하지 않는다. 별도 clone/worktree를 사용하면 병행할 수 있다. 운영 DB/생성 미디어/.env는 Git으로 합치지 않는다.
6. 브라우저에서 성공했다면 모의인지 실제인지, API/AI를 호출했는지, 자료/계정/버전·증거 위치를 적는다. 실제 첫 게시와 배포는 준비를 끝낸 뒤 교수 승인 범위에서 실행한다.

간단 작업 양식: **ID / 담당 / 기준commit / 문제와 재현 / 변경파일 / 완료기준 / 시험결과 / 남은것 / PR·패치·증거위치**.
